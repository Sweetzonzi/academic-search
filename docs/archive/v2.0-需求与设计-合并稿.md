## 0. 一页摘要

### 0.1 这是什么

一套**本地优先**的学术文献工作流：agent 通过公开数据库（OpenAlex、arXiv、Crossref）按用户研究领域检索论文 → 先用本地 Zotero 库去重 → 结果进"候选池" → 经筛选后写入 Zotero 成为正式条目 → 中文摘要与翻译缓存在本地 → 支持按需查阅、检索、精读、总结；未来扩展到引用图谱与研究脉络。它由**一个确定性 CLI**（干重活）+ **一个薄 SKILL.md**（告诉 agent 何时调用）+ **一个 sidecar SQLite**（存派生数据）组成，并与用户已有的 Zotero 库共用条目资产。

### 0.2 关键结论（十条）

1. **存储选型成立，但要两层，且权威按语料库划分**：Zotero 是「我的库」（人工策展的小库）的权威，sidecar 是「领域语料 + 候选池 + 派生数据」的权威，作品身份归 OpenAlex `work_id`；两者单向流动（promote），**没有字段两处可改**（§4-D1、§4-D8、§5.4）。
2. **当前最大阻塞是 Zotero 版本**：本机 **9.0.4**，本地 API 只读，且库从未同步（无 API key）→ **写入完全不可用**。Zotero **10.0（2026-08-17 发布，当前 10.0.6）新增本地 API 写入**，升级后一次弹窗授权即可获得完整 CRUD + 文件上传，**全程本地、不需要 zotero.org 账号**（§3.2）。
3. **OpenAlex 已改为按次计费 + 每日额度**：polite pool 于 2026-02 废除（`mailto` 被忽略），**无 key 仅 $0.10/天**，`search=` 比 `filter` **贵 10 倍**（实测响应头分别为 `0.001` / `0.0001` 美元/次）。→ 必须申请免费 key，并强制"优先 filter、`per_page=100`、结果落盘"（§3.4、§5.2）。
4. **不能盲信任何单一元数据源**：实测到 DOI↔标题错配、`ids.doi` 指向别的论文、权威论文缺 DOI/arXiv ID、按被引排序的头部是掠夺性期刊灌水论文。→ "可信"要靠显式质量闸门 + 全链路 provenance，不能靠数据源本身（§5.2、§5.10）。
5. **去重必须三层且离线优先**：本地 sqlite 查重（**不需要 Zotero 运行**）→ 远端结果集内部去重 → 候选池比对；预印本与正式版按"同一研究的两个 version"处理（§5.3）。
6. **全文有捷径**：本机 Zotero 已为 6/6 个附件生成 `.zotero-ft-cache` 纯文本（45KB–292KB），**默认不必解析 PDF**；只有需要版面/图表时才用 PyMuPDF（§5.5）。
7. **形态建议：确定性 CLI + 薄 SKILL.md**，不做常驻 MCP。对比：MCP server 默认 38 个工具的 schema 每次请求约 **13,448 tokens**；skill 只在目录里占 frontmatter（约 98 tokens），按需加载正文（约 1,368 tokens）（§4-D2、§5.7）。
8. **触发方式调度器中立**：采集命令必须是**无头 + 幂等 + 可观测**的 CLI，至于由谁定时——DSH schedule、Codex 等外部 agent 的定时任务、系统计划任务——都可以，设计不做取舍（§4-D5、§5.8）。
9. **单一检索入口消除"分叉"**：agent 只调用一个 `search/lookup`，内部按"本地 Zotero → 候选池 → 联网"顺序执行；sidecar 永不权威，删掉可重建（§4-D7、§5.4.4）。
10. **中文检索能力必须由 sidecar 提供**：实测 SQLite FTS5 默认分词器对中文 **0 命中**，改用 `tokenize='trigram'` 后命中，但 **2 字词仍失效**（需 `LIKE` 兜底或预先分词）（§5.4.5）。

### 0.3 立刻要做的三件事

1. 备份 `D:\ZoteroLib\zotero.sqlite`（2.22 MB）——升级前的安全检查。
2. 申请 OpenAlex 免费 API key（免费，额度 ×10）。
3. 做 M0 spike：升级 Zotero 10.0.6 → 授权 → 写一条测试条目再删除，确认链路与回滚（§7）。

## 1. 需求

### 1.1 原始需求（逐字引用）

> 现在打算做一套学术检索skill之类的东西给agent用于定时任务或用于回应用户的科研需求，能够让llm通过公开数据库如openAlex，arxiv等获取用户研究领域的有价值的可信的论文，存到本地，翻译摘要缓存，并能够按用户需求查阅检索总结阅读等。考虑可以访问本地的zotero sqlite存储，增删改查，而不是自己实现一套数据库体系。当然，网络查找论文前还应去重等。未来可能还有研究脉络可视化，顺着引用找上去之类的需求。分析分析这些需求。

### 1.2 需求解读（原话 → 可验收需求）

| 编号 | 原话依据 | 需求 | 可验收判据 |
|---|---|---|---|
| R1 | "用于定时任务" | 周期性的领域增量采集（由选定调度器无头触发） | 命令无头可跑、可重入；每次运行产出 `run.json` + 报告；重跑同一时间窗不产生重复候选 |
| R2 | "用于回应用户的科研需求" | 交互式按需检索与答疑 | 用户提问后，skill 被触发并在一次回答内给出带出处的结果 |
| R3 | "通过公开数据库如 openAlex，arxiv 等获取" | 多源检索（OpenAlex 主、arXiv 补预印本、Crossref 兜 DOI） | 单源不可用时链路仍能产出结果（降级而非失败） |
| R4 | "有价值的可信的论文" | 质量闸门 + 可溯源 | 每条结果带来源、获取时间与分级理由；撤稿/掠夺性期刊可被标记或过滤 |
| R5 | "存到本地" | 正式条目入 Zotero，派生数据入 sidecar，默认不下载 PDF | 条目在 Zotero UI 可见可管理；sidecar 删除后可从 Zotero + 网络重建 |
| R6 | "翻译摘要缓存" | 标题/摘要中文翻译与摘要生成，带缓存与失效 | 同一篇第二次请求零成本命中缓存；改提示词后旧缓存不命中 |
| R7 | "查阅检索总结阅读" | 本地检索、条目读取、总结、精读（含页码定位） | 结论可落到 `{work_id/doi, itemKey, 页码或段落}`；无出处的断言不输出 |
| R8 | "访问本地的 zotero sqlite 存储，增删改查，而不是自己实现一套数据库体系" | 复用 Zotero 作为条目存储；**读**走 sqlite（离线可用），**写**走 Zotero 官方通道 | 读取不要求 Zotero 运行；写入不直接改 `zotero.sqlite`（官方明确反对，见 §3.2 注） |
| R9 | "网络查找论文前还应去重" | 联网前先查本地与候选池 | 已在库的论文不会再被推荐或写入；同一 DOI 不产生第二条 |
| R10 | "未来……研究脉络可视化，顺着引用找上去" | 引用图谱：向后溯源 + 向前追踪 + 可视化 | 给定种子论文可产出可读的演进脉络图（远期验收） |
| N1 | "可信" | 可溯源、来源可验证、质量闸门、缺陷显式暴露 | 见 §5.10.1 |
| N2 | "（隐含）成本可控" | 外部 API 额度与 LLM token 双预算 | 每次 run 有预算上限与余额降级策略 |
| N3 | "（隐含）隐私" | 本地库内容默认不出网；可选全离线 | 云端调用内容可枚举、可关闭 |
| N4 | "（隐含）可维护" | 可重建、可回滚、接口契约稳定 | 一次 run 的入库可一键撤销；JSON 契约只增不删 |

### 1.3 使用场景

| 场景 | 触发 | 期望行为 |
|---|---|---|
| **S1 每周增量**（定时） | 任意调度器（DSH schedule / 外部 agent 定时任务 / 系统计划任务） | 抓取领域新论文 → 去重 → 质量分级 → 入候选池 → （可选）翻译摘要 → 产出 `reports/<date>.md` + `run.json` |
| **S2 会话内汇报**（定时 + 交互） | DSH schedule 或外部 agent 的定时任务唤醒 | 读最新 run 报告，提炼要点、指出异常、给出推荐阅读清单 |
| **S3 领域问答**（交互） | 用户问"最近有没有关于 X 的新方法" | 先查本地库与候选池，再联网补充，回答带出处 |
| **S4 精读与中文摘要**（交互） | 用户问"这篇讲了什么，跟我的方向什么关系" | 取全文（本地 ft-cache 优先）→ 生成中文摘要 → 在 Zotero 写入子笔记（若已入库） |
| **S5 归属确认**（交互） | 用户丢来一个 DOI/标题问"我库里有没有" | 命中则返回本地条目与所在 collection/标签，未命中则给出候选 |
| **S6 脉络追溯**（交互，远期） | 用户问"这个方向是怎么演进的" | 抓引用边 → 主路径/前后向链 → 输出 Mermaid/Graphviz 图 + 每节点一句话说明 |

### 1.4 范围与非目标

**在范围内**：英文文献为主的检索与入库；本地 Zotero 库的读与（升级后）写；中文翻译与摘要；引用图谱。**非目标（明确不做）**：① 替代 Zotero 的文献管理功能；② 自建条目数据库或元数据权威；③ 全量抓取出版商全文或整篇翻译分发；④ 覆盖 CNKI/万方等中文数据库（见 §9-未决）；⑤ 常驻 MCP 服务；⑥ 无人审批的全自动入库（默认可配置为需确认）。

### 1.5 成功标准

**必须成立**：同一查询重跑 0 条重复候选；已在库论文 0 次重复写入；未下载 PDF 的条目也能给出中文摘要；一次 run 的入库可一键撤销；删除 sidecar 后条目视图可由 Zotero + 网络重建一致（缓存除外）；采集命令无头可跑且产物为结构化报告（任何调度器都能驱动、任何 agent 都能读）。
**量化目标（待与实现者的预算对齐）**：单次 run 的 OpenAlex 花费 < 每日额度 20%；摘要命中缓存率 > 80%（稳态）；单条目的本地检索延迟 < 100 ms。

**一条容易被忽略的边界**：本地库目前只有 **5 条目 + 6 附件 + 1 个 collection（"世界模型"）+ 3 个 tag**（实测，附录 B）。因此本项目的定位是"**外源检索为主、本地库为锚**"，而不是"把已有库管起来"。

## 2. 术语表

| 术语 | 含义 |
|---|---|
| **agent skill / SKILL.md** | agent 按需加载的指令包：`<name>/SKILL.md`（YAML frontmatter 必填 `name`、`description`）+ 可选的 `references/`、`scripts/`、`assets/` 资源目录 |
| **DSH** | 本机运行的 DeepSeek Harness（本项目的 agent 宿主），提供 skill 装载、schedule 提醒、子 agent 等能力 |
| **MCP** | Model Context Protocol；把工具 schema 常驻注入模型上下文的一种接入方式（本项目不作为主路径） |
| **sidecar** | 挂在主系统旁边、只服务主系统、删掉不影响主系统的配套存储。本文中 = **一个 SQLite 文件** |
| **blob 目录** | 存放大块派生文本/页图的目录，**文件名 = 内容哈希** |
| **work / work_id** | 一篇"作品"的聚合身份；本文统一采用 OpenAlex Work ID（形如 `W2626778328`） |
| **itemKey** | Zotero 条目的稳定标识（`items.key`）；**不用自增 `itemID`**（重装/同步后会变） |
| **候选池（candidate）** | 检索结果在进入 Zotero 之前的暂存区，含评分、分级理由、状态 |
| **promote** | 把候选写入 Zotero 成为正式条目，并打 provenance 标记 |
| **provenance** | 来源与生成过程的记录：来源源、获取时间、原始响应、决策理由、模型与提示词版本 |
| **ft-cache** | Zotero 为每个已索引附件生成的纯文本全文缓存（`storage/<key>/.zotero-ft-cache`） |
| **FTS5 / trigram** | SQLite 全文检索模块；默认 `unicode61` 分词器对中文无效，需 `tokenize='trigram'` |
| **polite pool** | OpenAlex 过去靠 `mailto` 识别的免费高速通道，**已于 2026-02 废除** |
| **OA / TDM** | 开放获取 / 文本与数据挖掘（Crossref `link[]` 中的 `intended-application: text-mining`） |
| **run / run_id** | 一次采集执行及其标识，用于幂等、观测与回滚 |

## 3. 现状与约束（实测）

### 3.1 环境事实

| 项 | 实测值 | 对设计的影响 |
|---|---|---|
| Zotero 版本 | **9.0.4**（`D:\Zotero\zotero.exe`，2026-05-22），无进程运行 | 本地 API 只读 → **写入不可用** |
| 数据目录 | `D:\ZoteroLib`（由 `prefs.js` 的 `extensions.zotero.dataDir` 指定） | 路径不可写死，须从 prefs 解析 |
| 数据库 | `zotero.sqlite` 2.22 MB；`journal_mode=delete`、无 `-wal/-shm`、`integrity_check=ok`；`user_version=0` | 可直接复制为一致快照；读取安全 |
| 本地 API 开关 | `extensions.zotero.httpServer.localAPI.enabled=true`，但 23119 端口拒连 | 任何 API 路线都必须先拉起 Zotero |
| 同步状态 | 所有 items `version=0, synced=0`；无 API key；`groups` 为空 | **Web API 路线也不通** |
| 库规模 | 5 条目 / 6 附件 / 1 collection / 3 tag（CS-AI、CS-LG、Stat-ML）/ 28 creators | 定位为"锚"而非"主体" |
| 全文索引 | 6/6 附件已索引；`indexedPages` 等于 `totalPages`；`indexedChars` 列为 NULL（勿用于计数） | 全文检索不需要 PDF 解析 |
| 目录一致性 | `storage/` 有 13 个子目录，`itemAttachments` 只有 6 行（7 个孤儿目录，重复导入残留） | **遍历必须以数据库为准** |
| 运行时 | Python 3.12.14（DSH bundled，内置 sqlite 3.53.1，**FTS5 可用**）/ anaconda 3.12.7；**无 uv、无 sqlite3 CLI、无 pandoc、无 libreoffice**；`pymupdf` 有；`requests`/`PyYAML`/`feedparser`/`pyzotero` **缺失** | 核心链路建议只用标准库（§5.6.3） |
| 网络 | OpenAlex 200（约 0.9 s）、arXiv 200（约 1.2 s）、Crossref 200（约 1 s，**突发时实测 429**）、Semantic Scholar **429** | 主源直连可用，无需代理 |

### 3.2 Zotero 写入通道的三条路线（关键决策）

| 路线 | 前提 | 能力 | 评价 |
|---|---|---|---|
| **本地 API 写入** | **Zotero 10.0+**（当前 10.0.6，2026-10-07） | items/collections/saved searches 的 POST/PUT/PATCH/DELETE、标签删除、全文写入、三阶段文件上传（<4 GB） | ✅ **推荐**。官方支持、全程本地、不需要 zotero.org 账号、UI 立即生效、无速率限制。授权：`POST /api/local/authorize` + `Zotero-Server-ID` 头，用户点"Always Allow"得可复用 key；弹窗限 5 次/分；默认单次 key |
| Web API | zotero.org 账号 + 开启同步 + API key | 同上（云端路径） | 可行但需把库同步上云（隐私/流量），且有 429 与并发限制（官方建议不超过 4 并发） |
| 连接器通道 | Zotero 运行中（**9.x 亦可用**） | `POST /connector/import`（BibTeX/RIS/CSL JSON 等字符串）、`POST /connector/saveItems`（Zotero JSON 数组） | ⚠️ 复用浏览器连接器协议（源码 `server_connector.js:293-344`、`794-846`），**非公开 API**；**目标集合 = UI 当前选中集合 / `lastViewedFolder`**，不受调用方控制。仅作 9.x 回退或人工确认后的批量导入 |

> **为什么不直接写 `zotero.sqlite`**：Zotero 官方立场是"只读"——其缓存层会破坏 SQLite 文件锁，**运行中修改极易损坏数据库**，且绕过数据校验与外键检查。本项目遵守该约束：读用副本，写走官方通道。

**降级方案**：若不升级 Zotero，则"候选池停在 sidecar + 生成 RIS/BibTeX 供人工或连接器导入"；检索、去重、翻译缓存、阅读总结全部不受影响，只有"agent 自主增删改库"受限。

### 3.3 依赖与运行时策略

核心链路**只用标准库**（`urllib.request`、`json`、`sqlite3`、`xml.etree` 解析 arXiv Atom），做到"零安装可运行、定时任务不因环境漂移而失败"；重活（向量、PDF 版面、Zotero 客户端库）放独立虚拟环境按需启用。

### 3.4 数据源可达性与配额（实测）

| 源 | 可达性 | 配额 / 计费 |
|---|---|---|
| OpenAlex | 200，约 0.9 s | **按次计费 + 每日额度**：无 key `x-ratelimit-limit-usd: 0.1`；`filter` 查询 `cost 0.0001`；`search=` 查询 `cost 0.001`；免费 key ≈ $1/天；速率 10/30/50 req/s（无 key/免费 key/年费） |
| arXiv | 200，约 1.2 s | 无 key；**每 3 秒 1 请求、单连接**；单次 ≤2000 条、总量 ≤30000 条；新文章午夜后才可见 |
| Crossref | 200，约 1 s；突发 429 | Public 5 req/s；Polite（`mailto` + 识别性 UA）10 req/s、并发 3 |
| Semantic Scholar | **429**（实测） | 无 key 为全平台共享 1000 RPS（高峰期限流）；有 key 仅 1 RPS → 仅作可选增强 |
| Unpaywall / CORE / DOAJ | 未逐一实测 | Unpaywall 须真实 email（假邮箱 422）；CORE 每 10 秒 1 批；DOAJ 每 2 秒 2 次。三者的每日上限**未查证** |

**额度实测后果**：本轮十几条探测请求把当天 $0.10 额度消耗到剩 `0.0235`（`x-ratelimit-remaining: 235`，约 13.8 小时后重置）。→ 定时任务若不申请 key 必然撞墙。

## 4. 关键设计决策（ADR）

每条格式：**决策 / 理由 / 被否决的备选 / 代价**。

### D1 采用「Zotero + sidecar + blob 目录」三层存储，而不是单一存储

- **理由**：Zotero 的 `itemData` 是固定字段集的 EAV（`itemData(itemID, fieldID, valueID)`，无 `key/version`），**结构上装不下**"中文摘要 + 模型版本 + 源哈希"这类任意派生字段；而候选池、评分、引用边属于"工作台状态"，不该成为用户资产。
- **否决**：① 全部塞进 Zotero（`Extra` 字段 / 笔记）→ 污染库、无类型化列、无法用 SQL 查、随导出泄漏；② 自建完整条目库 → 违背 R8，且条目管理是 Zotero 的强项。
- **代价**：多一个文件与一层 join；需要"权威边界"纪律（§5.4.2）。

### D2 采用「确定性 CLI + 薄 SKILL.md」，而不是常驻 MCP

- **理由**：分页、限流、去重、幂等、事务、预算都应由代码保证，LLM 只做查询扩展、筛选与总结；上下文成本上，MCP 默认 38 个工具 schema 每次请求约 **13,448 tokens**，而 skill 目录只花 frontmatter 约 **98 tokens**，正文按需 **1,368 tokens**（数据来自已克隆的 `zotero-mcp` 度量脚本与测试断言）。
- **否决**：MCP server（低频高价值场景下常驻代价过高）；"把逻辑写进 SKILL.md 让 LLM 自己编排"（不可复现、不可测试、易烧额度）。
- **代价**：需要维护 CLI 的参数、JSON 契约与退出码约定。

### D3 作品身份统一到 `work_id`（OpenAlex Work ID），DOI/哈希降级为别名

- **理由**：实测 DOI 会**缺失**（权威论文无 DOI）、会**错配**（DOI 对应到别的标题）、**一篇多个**（预印本 + 正式版）；哈希回答的是"内容变了没有"，用它当身份会在重抓时凭空产生重复。
- **否决**：以 DOI 为主键；以标题哈希为主键；以 arXiv ID 为跨源枢纽（OpenAlex `ids` **不含 arXiv 键**）。
- **代价**：需要 `work_alias` 别名表与一致性校验（§5.3.4）。

### D4 中文摘要写回 Zotero 时用 **child note**，不改 Abstract 字段、不塞 Extra

- **理由**：child note 不破坏元数据、可批量识别与回滚、点开即读；`Abstract` 字段会**覆盖原文摘要**且污染导出；Extra **不是自由文本框**——Zotero 按 `字段名: 值` 行语法解析并在保存时规范化（源码 `item.js:311`、`item.js:5375-5679`），内容还会随 BibTeX 等导出泄漏。
- **否决**：写入 Abstract；写入 Extra；写成 `.md` 附件（`.md` 通常不被 Zotero 全文索引，且占附件位）。
- **代价**：条目树笔记变多；若日后开启 Zotero 同步，这些笔记会上传到 zotero.org。

### D5 调度器中立：只约束命令的性质，不规定用哪个调度器

- **决策**：采集入口是一个**无头、幂等、可观测**的 CLI 命令；调度由使用者的现有工具承担——**DSH schedule、Codex 等外部 agent 工具的定时任务、系统计划任务（Windows 任务计划程序 / cron）任选，可组合**。
- **理由**：调度是部署选择而非设计约束。只要命令无头、可重入、产物是结构化报告，任何调度器都能驱动它，也能被任意 agent 读取；把调度器写死在设计里会无谓地限制使用场景。
- **约束（必须守住的三条）**：① **无头**——不得依赖 GUI、TTY 或交互确认；② **幂等**——同参数重跑不产生重复候选/重复入库；③ **可观测**——每次运行产出 `run.json` + markdown 报告，使"调度器只负责触发、agent 只负责读报告"成为可能。
- **被否决的备选**：把采集逻辑做进某个特定 agent 的会话内（换 agent 就得重写）；要求人类在触发点点击确认（破坏无人值守）。
- **代价**：需要维护 run 账本与报告格式的稳定性（`SCHEMA_VERSION` 只增不删）。

### D6 默认**不下载 PDF**，按需获取，且只取 OA 版本

- **理由**：元数据 + 摘要足够支撑检索、去重与初筛；避免版权风险、存储膨胀与"两份 PDF 不知哪份是新的"。
- **否决**：全量预下载（成本与合规风险）；完全不下载（精读场景需要正文）。
- **代价**：精读时需要一次网络往返；OA 覆盖率不足时可能取不到全文（记录原因即可）。
- **落地形态**：promote 出来的是**仅元信息条目**（Zotero 支持无附件条目，见 §5.4.8）；PDF 在首次精读时补挂到**同一个条目**上。

### D7 检索入口唯一：`search` / `lookup --scope auto`，内部固定三段顺序

- **理由**：分叉的真正风险是"两个入口"或"同一事实能改两处"。唯一入口 + 按字段划分权威可消除该风险，同时保留"联网前先查本地"的初衷（R9），且本地查询**零网络、零费用、毫秒级**。
- **否决**：让 agent 分别查询 Zotero 与 sidecar 再自行合并（易漏、口径不一）；把本地库镜像进 sidecar（变成影子库）。
- **代价**：CLI 需实现多后端聚合与结果标注（§5.4.4）。

### D8 权威归属：Zotero 管「我的库」，sidecar 管「领域语料 + 派生数据」，并定义冲突规则

- **决策**：**两个语料库、两种权威**，而不是让某一方通吃。
  - 「**我的库**」（人工策展，10²–10³ 量级）→ **Zotero 权威**
  - 「**领域语料 / 候选池 / 图谱语料**」（机器规模，10³–10⁵ 量级）→ **sidecar 权威**
  - 作品身份 → **OpenAlex `work_id` + 别名表**（第三方标识权威，不归任何一方）
  - `promote` 是**单向复制 + provenance**，不是双向同步；反向只有"读"（把 Zotero 条目读进来做去重与关联）
- **理由**：① Zotero 的价值在"人会在 UI 里编辑、需要同步/导出/引用格式化、有阅读器与标注"，这些只对**人工策展的小库**成立；② 把机器规模的语料（几千到几万篇）塞进 Zotero 会污染用户库、拖慢 UI、放大同步成本，而它又提供不了图查询；③ 反过来把"我的库"搬进 sidecar，等于放弃 Zotero 的阅读器、标注、Word 引用插件，并要重建条目模型与导出——这正是 R8"不自建数据库体系"要避免的；④ 两个库各自权威、只在一处单向流动，就不存在"同一份数据两处可改"的悖论。
- **冲突规则（元数据层面，四条）**：
  1. **人工优先**：Zotero 侧的人工编辑永远胜出，agent 永不静默覆盖。
  2. **不合并、只失效**：检测到 Zotero 条目变化（`dateModified`/`clientDateModified`，Zotero 10+ 还可用本地 `version`）→ 把相关派生缓存标记 stale 并按需重算，**不尝试 diff 合并**。
  3. **写入显式且可追溯**：agent 修改 Zotero 元数据只能是显式命令，默认**只补空、不改非空**（fill-if-empty），并记录 `run_id` 与理由。
  4. **冲突显式暴露**：与 Zotero 不一致的外部元数据标记 `metadata_conflict`，进 run 报告，等人决定。
- **被否决的备选**：
  - **sidecar 作为唯一权威，Zotero 只当镜像/导出端**：写入 Zotero 的通道约束（10+、HTTP、无跨库事务）**一个都不会减少**——换权威不解决写入问题，只额外背上镜像维护、附件管理、引用格式化与同步的负担，并直接作废 R8。**只有当用户实际上不使用 Zotero UI 时才值得重新评估**（见下）。
  - **双向同步**：冲突不可判定，必然出现"谁覆盖谁"的静默数据丢失。
- **代价**：需维护 `dateModified`/`version` 快照与 stale 检测；"我的库"与"领域语料"的边界必须在命令上显式区分（`--scope local` vs `--scope corpus`）。
- **诚实记录的翻转条件**：如果用户**实际上从不打开 Zotero**，只把它当存档/导出端，那么 Zotero 权威带来的好处（人工策展、同步、阅读器）不成立，而写入约束仍然存在——此时"以 sidecar 为主、Zotero 仅作导出"才是更优解。该问题列为待决策项（§10-8）。

                              ┌──────────▼───────────────────────────┐
   任意调度器 ──定时──▶       │  academic-search CLI（确定性）        │

### 5.2 数据源层

**分工**（详细配额见 §3.4）：

| 源 | 定位 | 关键字段/能力 |
|---|---|---|
| **OpenAlex** | 主力元数据 + 引用图谱 | `ids/doi`、`abstract_inverted_index`（倒排索引需还原）、`referenced_works`、**`filter=cites:<id>`（向前被引，实测可用）**、`related_works`、`topics/keywords`、`fwci`、`citation_normalized_percentile`、`is_retracted`、`open_access.oa_status`、`best_oa_location.pdf_url`、`counts_by_year`、`language`、`select=` 瘦身（仅顶层字段）、`cursor=*` 游标分页（普通分页上限 10000 条） |
| **arXiv** | 预印本、最新进展 | Atom：`id`（含版本，无版本号=最新）、`published/updated`、`summary`、`authors`、`categories`、`arxiv:doi`、`arxiv:journal_ref`、`arxiv:comment`（实测均存在）；`sortBy=submittedDate` 用于追新 |
| **Crossref** | DOI 权威兜底、卷期页码、参考文献 | `query.bibliographic`、`is-referenced-by-count`、`link[]`（含 `content-version: vor` 的 TDM 链接）、**默认返回 `reference[]`**（实测 52 条，可在无 S2 时补引用边） |
| **S2（可选）** | 引用语境、TLDR、影响力加权 | `tldr`、`influentialCitationCount`、`/citations`、`/references`、`/paper/search/bulk` |
| **Unpaywall / CORE / DOAJ（可选）** | OA 定位与白名单 | Unpaywall `best_oa_location`；CORE 全文；DOAJ 用于 OA 期刊白名单 |

**摘要获取**：OpenAlex 以倒排索引给出（`{token: [pos,…]}`，因法律原因不提供纯文本），需还原为有序文本（实测还原出 1260 字符）；arXiv 直接给 `summary`。覆盖率不完整（官方口径：2022 年后 >60%、2000 年前约 45%）→ 摘要缺失是正常分支（回退 Crossref/arXiv 或标记"无摘要"），并**原样缓存**。

**质量闸门（"可信"的可实现部分）**：`is_retracted`、`type`（排除 paratext / editorial/erratum）、`primary_location.source.type`、OA 状态与许可、`fwci`/`citation_normalized_percentile`、`counts_by_year` 异常检测（单年暴涨 → 灌水嫌疑）、venue 白名单（领域顶刊顶会 + DOAJ）、venue 黑名单（掠夺性/已知灌水刊）、语言、年份窗口、机构与通讯作者匹配。
**输出形态**：**分级（A/B/C）+ 理由**，不做二元淘汰；理由随候选落库以便复盘调参。

**实测坑（每条均为真实请求结果，详见附录 B）**：

1. **自由文本噪声极大**：`search=attention is all you need` 命中 **3,208,007** 条 → 自由文本只用于"发现"，不用于"判定存在"；存在性判定走结构化 `filter`。
2. **权威记录可能无 DOI/arXiv ID**：`W2626778328`（"Attention Is All You Need"）`type=preprint`、`publication_year=2025`、11 个 location、`ids.arxiv=None`。
3. **DOI 与标题可能错配**：`10.48550/arXiv.2210.03629` 返回记录的标题是另一篇论文；GPT-4 报告的 `ids.doi` 指向 `10.4230/lipics.cosit.2024.11` → 命中后必须做一致性校验（标题相似度/年份/作者），冲突则降级为"候选 + 待人工确认"，并保留原始响应。
4. **质量陷阱**：按被引排序的头部是 OA 期刊灌水论文（`fwci=136`、单年 1310 次引用、`citation_normalized_percentile≈0.99999`）。
5. **filter 值必须转义**：标题含 `,` 或 `:` 会直接 400（实测触发）。
6. **语法有新旧之分**：`filter=title_and_abstract.search:` 与 `default.search:`（后者是 `fulltext.search` 的弃用别名）仍可用但已弃用；新写法是 `search=` 与 `search.title_and_abstract=`。`select=` **只能选顶层字段**；文档 `per_page` 上限 100（实测 200 仍返回 200 条，但不要依赖）；整条 URL 上限约 4 KB，超长布尔查询需分块后取并集。
7. **增量入口不确定**：`from_created_date`/`from_updated_date` 被文档标注为付费计划功能，**实测无 key 返回 429**（数秒后的其它查询正常）→ 每日增量改由"`publication_date` 回看 + 本地去重"实现；`updated_date` 因引用数重算而变动，是噪声源。
8. **跨源字段现实**：OpenAlex `ids` 不含 arXiv 键（arXiv 副本体现为 `locations[]` 的 `pmh:oai:arXiv.org:…`）；`referenced_works` 会短于原文参考文献表 → 引用图谱需多源拼装。

### 5.3 身份与去重层

#### 5.3.1 三层去重

```
第一层 本地离线查重（读 zotero.sqlite 副本，Zotero 不必运行）
   key1 = normalize_doi(doi)         # 去 https://doi.org/ 前缀、大小写折叠（不改写后缀字符）
   key2 = arxiv_identity(arxiv_id)   # 去版本号 vN；无版本号 = 最新版
   key3 = normalize_title(title)     # NFKD + 去标点 + 折叠空白 + 去首冠词
   命中任一 → 视为"已存在"，返回本地 itemKey
第二层 远端结果集内部去重
   同 DOI / 同 arXiv identity / 标题折叠相同 → 合并
   预印本↔正式版 → "同一研究的两个 version"：保留主记录 + 记录 version 关系
   线索：arXiv 的 arxiv:doi / journal_ref；OpenAlex locations[].version
        = submittedVersion / acceptedVersion / publishedVersion，type=preprint vs article
第三层 候选池比对（sidecar）
   以 work_id / doi / title_key 建唯一索引，跨 run 不重复推荐
```

#### 5.3.2 可复用实现

`zotero-mcp/src/zotero_mcp/identifiers.py`（347 行、纯标准库、作者明确声明可外部 import）提供 `normalize_doi`/`doi_match_key`/`arxiv_identity`/`normalize_title_for_matching`（NFKD + 标点归一 + 去首冠词，与 Zotero 自身 `duplicates.js` 对齐）。

#### 5.3.3 缺口

其标题匹配只做精确折叠，**无编辑距离、无"作者 + 年份 + 副标题"模糊启发式**；且它的查重走 Zotero 客户端库（Zotero 未运行即不可用）——本项目必须自研离线模糊匹配层。

#### 5.3.4 一致性校验（防错配）

按 DOI 命中后，用**标题相似度 + 年份 + 首作者**做交叉校验；任一项严重冲突则：保留记录但标记 `metadata_conflict`，进入"待人工确认"，不静默采用。

### 5.4 存储层

#### 5.4.1 三分工

| 存储 | 装什么 | 类比 |
|---|---|---|
| Zotero（`D:\ZoteroLib`） | 条目、collection、tag、附件 PDF、笔记、标注、全文索引 | 书架与正式资产 |
| sidecar（一个 `.db`） | 别名、派生文本缓存、引用边、候选池、运行账本 | 卡片柜与借阅台账 |
| blob 目录（`cache/ab/cd<hash>.txt`） | 大块派生文本/页图，**文件名 = 内容哈希** | Zotero 的 `storage/`，改为哈希命名 |

#### 5.4.2 权威边界（防分叉的核心规则，依据 D8）

**两个语料库、两种权威**：

| 语料库 | 规模量级 | 权威 | 内容与访问方式 |
|---|---|---|---|
| **我的库**（人工策展） | 10²–10³ | **Zotero** | 条目、标签、collection、附件、笔记、标注、全文索引；**读** = 只读 sqlite 副本（`items`/`itemData`/`itemTags`/`fulltextItems`）+ `.zotero-ft-cache`；**写** = Zotero 官方 API（10+ 本地 / Web API） |
| **领域语料 + 候选池 + 图谱语料**（机器生成） | 10³–10⁵ | **sidecar** | 检索结果、评分与理由、引用边、翻译与摘要缓存、运行账本；SQL + FTS5 |
| 作品身份 | — | **OpenAlex `work_id` + 别名表** | 跨源身份由第三方标识体系提供，不归任何一方 |

**流动是单向的**：`领域语料 --promote--> 我的库`（带 provenance、可回滚）；反向只有"读"——把 Zotero 条目信息读进来做去重与关联，**不做把用户库倒灌进语料库的同步**。

**冲突规则（元数据，四条）**：① 人工优先——Zotero 侧编辑永远胜出，agent 不静默覆盖；② 不合并、只失效——发现条目变化（`dateModified`/`clientDateModified`，10+ 另有本地 `version`）即把相关缓存标 stale 重算；③ 写入显式——改 Zotero 元数据必须显式命令，默认**只补空、不改非空**；④ 冲突暴露——与 Zotero 不一致的外部元数据标记 `metadata_conflict` 并进报告。

**没有任何字段同时存在两处**；唯一冗余是 `work_id ↔ itemKey` 指针，属刻意设计的桥梁。完整视图在内存中 join，不落第二份库。

#### 5.4.3 sidecar 三条原则

1. **Zotero 是唯一权威**：sidecar 里没有"只此一份"的数据，整个文件删掉，用户库毫发无损。
2. **不重复 Zotero 已有的东西**：元数据以 Zotero 为准；PDF 只存 Zotero 一份。
3. **只装可重建的派生数据**。
   另附工程要求：外键用 `libraryID + itemKey`；**按 `Zotero-Server-ID` 分区**（Zotero 10+ 版本号为本机局部版本，官方要求跨运行缓存按 server ID 分区）；`schema_version` + 迁移脚本；单写者 + WAL。

#### 5.4.4 单一检索入口（消除"分叉"）

```
lookup(DOI | arXiv ID | 标题 | 关键词 | 标签)
  ① 本地 Zotero（只读副本，离线、零成本、毫秒级）
       命中 → 返回条目 +「已在库」+ 附 sidecar 中文摘要（若有）
  ② sidecar 候选池（避免重复推荐、避免重复计费）
       命中 → 返回候选 + 评分与理由
  ③ 均未命中 → 联网 OpenAlex/arXiv，结果先与 ①② 去重，再落候选池
```
三类检索的落点：**DOI/arXiv ID** → Zotero 的 DOI 字段 + sidecar 别名表，两路合并去重；**标签** → 只查 Zotero（标签权威在该处，agent 自动打的标签也写进 Zotero）；**关键词** → Zotero 标题/作者 + `.zotero-ft-cache`，加 sidecar 中文摘要 FTS5。

**真正需要警惕的三件事（均属去重问题，不是存储分叉）**：① 用户自己导入的重复条目（Zotero 自带检测只做 DOI/标题精确折叠，且超 5000 条拒绝扫描）；② 预印本与正式版各存一条；③ Zotero 条目与 OpenAlex 记录是同一篇（靠 `work_alias` 命中）。

#### 5.4.5 中文摘要的可见性（写回 Zotero 的四种位置）

**默认看不到**：sidecar 内容不出现在 Zotero UI。要让中文摘要在 Zotero 里可见，必须写回——而这一步**当前被 9.0.4 卡住**（与 §3.2 同一决策）。

| 位置 | 可见性 | 代价 | 结论 |
|---|---|---|---|
| **child note** | 条目面板 Notes 区，点开即读，可被搜索命中（建议 `Everything` 模式） | 条目树变长 | ✅ **默认**（标题固定前缀，如「AI 中文摘要」） |
| Abstract 字段 | 最显眼（面板顶部，列表可加列） | **覆盖原文摘要**、污染导出 | ❌ |
| Extra 字段 | 列表可加列扫读 | 行语法解析 + 导出泄漏 | ⚠️ 仅极短单行 |
| `.md`/`.html` 附件 | 附件区双击打开 | 通常不被全文索引、占附件位 | 备选（长报告） |

**默认策略**：未入库候选只在 sidecar；`promote` 的条目写一条 child note：「一句话要点 / 中文摘要 / 关键词 / 来源 URL / 生成时间 / 模型与提示词版本」，提供 `--no-note` 开关；回滚按"前缀 + `run_id`"定位删除。

**中文检索的实测约束**：FTS5 默认 `unicode61` 分词器对中文 **0 命中**（实测「剩余使用寿命」「世界模型」「寿命预测」全空）；`tokenize='trigram'` 可用，但 **<3 字**的查询仍失效（实测「模型」「寿命」「世界」全空）→ 方案：trigram 索引 + `LIKE '%…%'` 兜底（或先用 jieba 分词再索引）。

#### 5.4.6 候选池 → 入库（promote）

```
search → candidates(sidecar：评分/分级/理由/来源)
  → [LLM 初筛 或 人工确认]
  → promote：写入专用 collection（如 `Agent Inbox/<领域>`）+ provenance tag（如 agent/2026-10）
             + sidecar 记录 run_id / 决策理由 / 原始响应快照
  → 回滚：按 run_id 找 itemKey → 删除（Zotero 删除进回收站，安全）
```
**这是最重要的安全阀**：agent 往用户的学术资产库里写东西，必须"可批量识别、可批量撤销"；绝不写进用户现有 collection。

#### 5.4.7 附件与 PDF

优先级（只取 OA）：① OpenAlex `best_oa_location.pdf_url` / `open_access.oa_url`；② Crossref `link[]`（`content-version: vor` + `intended-application: text-mining`）；③ Unpaywall `url_for_pdf`（常为 null，退到 `url_for_landing_page` 再解析）；④ arXiv / PMC 直链；⑤ 放弃并记录原因。落法：Zotero 10 三阶段上传（推荐）或工作区文件 + 链接附件。

#### 5.4.8 仅元信息条目（无附件）—— Zotero 完全支持，且应作为默认形态

- **对象模型**：Zotero 里"元数据条目"与"附件"是**两个独立的 item**（`items` + `itemTypes` 区分；附件另有 `itemAttachments.parentItemID` 指向父条目）。**没有任何字段要求条目必须有附件**；`fulltextItems` 只为"已索引的附件"建行，没有附件的条目就是没有那一行。
- **本机实测**：5 个顶层条目各有 1 个附件（6 个附件、6 条全文索引）；另有 **1 个 `parentItemID IS NULL` 的独立附件** → 反向证明 Zotero 允许"有文件无父条目"，自然也允许"有条目无文件"。
- **能力差异**：有元数据即可做——检索（标题/作者/年份/DOI/标签）、collection 归类、去重、引用与参考文献导出、元数据同步（**不占文件配额**）、写笔记（含中文摘要 child note）。缺附件则不能做——阅读与标注、该条目的全文检索、页码定位。
- **由此确定策略**（配合 D6）：**默认 promote 为仅元信息条目**；PDF 采用"**按需获取**"——用户第一次要求精读时才取 OA 全文，作为子附件挂到**同一个条目**上（Zotero 10 三阶段上传），**不重建条目、不影响去重键、不产生第二份 PDF**。
- **工程要求**：全文相关查询一律 **LEFT JOIN**（`itemAttachments` / `fulltextItems` 缺行是正常状态而非错误）；sidecar 的 `text_cache` 与 `zotero_link` 允许 `zotero_attachment_key` 为空。

#### 5.4.9 复现语义：第二次检索到同一篇（且它没进 Zotero）会发生什么

这是"候选池长期存在"带来的核心行为，必须写死，否则实现时容易出现两种错误：**每次都重算（浪费）**或**每次都跳过（错过撤稿与状态变化）**。

**命中判定**：第三层（候选池）按 `work_id` / DOI / `title_key` 命中 → **不新建候选、不重新计费检索、不重新调 LLM**，只做"刷新 + 决策保持"。

| 动作 | 内容 | 频率/成本 |
|---|---|---|
| **刷新（每次做）** | `cited_by_count`、`counts_by_year`、`fwci`、`citation_normalized_percentile`、**`is_retracted`（必查，安全信号）**、`oa_status` 与 `best_oa_location.pdf_url`（PDF 可能新出现）、`type`/venue（预印本可能已正式发表）、`refreshed_at`、`seen_count`、`last_seen_at` | 便宜：可**批量按 ID 取**（实测 `filter=ids.openalex:W1\|W2\|W3` 一次取回 3 条，花费 `$0.0001`；OR 值上限 100） |
| **重算（因输入变化）** | 质量分级（其输入含引用信号）→ 分数可能变；引用边（若该 work 在图谱范围内） | 纯规则计算，**不调 LLM** |
| **复用（缓存命中即不重算）** | 标题/摘要的中文翻译、各粒度摘要、嵌入向量 | 0 成本 |
| **保持（绝不重置）** | `status`（尤其 `rejected`）、`staged_at`、用户/AI 已做的决策与理由、`run_id` 归属 | — |

**重新翻译的唯一触发条件**（只与"源文本 + 生成参数"有关）：
1. **源文本变了**——OpenAlex 补全了 `abstract_inverted_index`；或 arXiv 出了 v2 改了 `summary`（版本更新会改摘要，这是真实情况）；
2. **生成参数变了**——`model_id` / `prompt_version` / `glossary_version` / `target_lang`。

**关键边界（实现时最容易犯的错）**：**引用数绝不能进缓存键**。缓存键是 `sha256(源文本 ‖ 目标语言 ‖ 模型 ‖ 提示词版本 ‖ 术语表版本)`，而 `cited_by_count` 属于"展示与排序输入"。若把整条记录哈希当缓存键，每次引用数变动都会导致全量重翻译。

**抑制规则**：`rejected` 的候选进入抑制名单（默认长期有效，可选 6–12 个月后允许重新浮现，因为研究兴趣会变），避免每轮都推荐同一篇被否掉的论文。

**与 Zotero 的衔接**：
- 候选被 `promote` → 记录标 `promoted` 并写 `zotero_link`；**此后该论文的命中走第一层（本地库），不再走第三层**。
- 若用户在 Zotero 中把该条目删除 → `zotero_link` 失效，标 `promoted_then_removed`，**不自动重新入库**（尊重用户的删除决定），但它仍留在候选池里可被查阅。

**成本对比（一句话）**：命中候选池的重复检索 ≈ `$0.0001` + 0 次 LLM 调用；重新翻译摘要 ≈ 1 次 LLM 调用。两者相差若干数量级，所以"缓存命中只刷新引用数"是必须实现的性质，而不是优化项。

### 5.5 缓存层

**键设计范式**（照搬 `zotero-mcp/src/zotero_mcp/fulltext_cache.py` 的内容哈希 + profile + 落库即逐出；其原则："文件变了必然换 hash，绝不供给陈旧文本"）：

```
cache_key = sha256(source_text_or_content_hash ‖ target_lang ‖ model_id
                   ‖ prompt_version ‖ glossary_version)
```
把 `prompt_version` 纳入键，是避免"改了提示词却读到旧摘要"的关键。

| 缓存 | 失效触发 | 备注 |
|---|---|---|
| 翻译（标题/摘要/关键词） | 源文本、目标语言、模型或 `prompt_version` 变化 | **不整篇翻译**（成本 + 版权） |
| 摘要（分层） | 同上 + 摘要粒度（一句话/贡献点/方法-结果-局限） | 粒度不同即不同条目 |
| 抽取全文 | 附件内容哈希变化 | 原始文本永久可复用 |
| 向量 | 嵌入模型或维度变化 | 需重建索引 |

**全文通道优先级**：① `.zotero-ft-cache`（零成本，本机 6/6 命中）→ ② Zotero 全文 API（10+ 可 `GET/PUT .../fulltext`，可写回改进后的文本）→ ③ PDF 自解析（`pymupdf` 已装）。
**成本控制**：批量走 Batch API（`zotero-mcp` 的 `openai_batch.py`/`batch_common.py` 有完整范式）；每个 run 设 token 预算，超限降级为"只翻标题"。

### 5.6 检索与命令接口

#### 5.6.1 命令面（初版）

| 命令 | 作用 | 关键约束 |
|---|---|---|
| `search` | 按领域/关键词/作者/机构检索，返回分级候选 | `--since`、`--limit`、`--source`、`--scope auto\|local\|remote` |
| `lookup` | 按 DOI/arXiv ID/标题取条目或候选 | 走 §5.4.4 三段顺序 |
| `dedupe` | 对给定集合做三层去重（离线优先） | 只读 sqlite，Zotero 不必运行 |
| `stage` | 候选落 sidecar（带理由与原始响应） | 幂等，唯一索引 |
| `promote` | 候选入 Zotero（专用 collection + provenance tag） | `--dry-run` 先行；可按 `run_id` 回滚 |

#### 5.6.2 输出契约

沿用 `zotero-mcp/cli_json.py` 的信封：**单一 `{ok, command, schema: 1, data | error{message, code}}`**，成功失败都写 stdout，日志写 stderr，`SCHEMA_VERSION` **只增不删**；退出码 0 成功 / 1 失败（可加细分码）。理由：agent 用同一套解析逻辑处理所有命令，定时任务易于校验。

核心链路仅标准库（见 §3.3）。

### 5.7 Skill 打包与装载

**三层结构**：

```
academic-search/            # skill bundle
├─ SKILL.md                 # frontmatter: name + description(触发条件)；正文=决策树与命令示例
├─ references/              # 按需加载：openalex-fields.md / arxiv-syntax.md / zotero-write.md / dedupe-rules.md
└─ scripts/                 # 确定性 CLI 实现
```

**装载位置（实测，DSH 扫描顺序）**：`<projectRoot>/.dsh/skills`(100) → `<projectRoot>/.agents/skills`(200) → `customSkillDirs`(300) → `~/.dsh/skills`(400) → `~/.agents/skills`(500) → bundled(600)；**`projectRoot` = 最近的含 `.git` 的祖先目录**（本工作区 `D:\Files\Project_Paper` 与 `D:\Files` 均无 `.git`，故取 cwd）。
**格式**：`<name>/SKILL.md` 目录 bundle 或 `<name>.md` 平铺；frontmatter 必填 `name`（kebab-case）与 `description`，可选 `whenToUse`/`metadata`/`user-invocable`/`disable-model-invocation`；发现深度仅一层；新增/改名**热更新**。定时任务可能在别的 cwd 的会话触发，**建议同时装到 `~/.dsh/skills/`**。

**SKILL.md 应写死的硬规则**：① 检索必须走 `--scope auto`（先本地后网络）；② 结论必须带出处，无出处不输出；③ 入库只能进专用 collection 且先 `--dry-run`；④ 余额不足或额度耗尽时降级而非重试。

### 5.8 触发方式与运行账本

**调度器中立**：本设计**不规定用哪个调度器**，只规定被调度的那个命令必须满足三条性质——**无头**（不依赖 GUI 或交互）、**幂等**（同参数重跑不产生重复副作用）、**可观测**（产出 run 记录与报告）。以下任一方式都可以直接驱动它：

```
# 采集（可被任意调度器无头调用）
academic-search sync --profile <领域> --budget <n>
  → 抓取增量 → 去重 → 分级 → 入候选池 →（可选）翻译摘要 → 写 reports/<date>.md + run.json
  → 不需要 LLM 或仅用批量 API；失败可重试、有日志

调度器（任选，可组合）：
  · DSH schedule（如每周一 09:00 唤醒会话：读最新 run 报告 → 要点提炼 / 异常提示 / 推荐阅读）
  · 外部 agent 工具自带的定时任务（如 Codex 等的 scheduled tasks），由它调用上述命令或读取报告
  · 系统计划任务（Windows 任务计划程序 / cron）
```

**幂等与水位**：sidecar 存 `last_success_watermark` 与 `run_id`；每次 run 独立事务；唯一索引保证重跑不产生重复候选。
⚠️ **增量策略**：`from_created_date`/`from_updated_date` 疑似付费层（§5.2 坑 7），因此采用"`publication_date` 回看 N 天 + 本地三层去重兜底"，并记录已抓取 `work_id` 以避免重复计费。
**限流与预算**：单次 run 的请求数/并发/退避上限显式配置；每次响应读 `x-ratelimit-remaining-usd`，低于阈值降级；arXiv 严格 3 秒间隔且**一天一次足够**（新文章午夜后才可见）；Crossref 走 polite 通道；S2 失败不阻断主链路。
**观测**：JSONL 结构化日志 + markdown 报告（新增候选、去重拦截、入库数、失败源与原因、token 与费用消耗）。报告要能被"外部 agent 只读消费"，因此除 markdown 外必须同时产出结构化 `run.json`。

### 5.9 引用图谱与研究脉络（未来）

**数据基础（实测确认）**：OpenAlex 向后 `referenced_works`（示例 18 条；官方明确可能短于原文参考文献表）、向前 **`filter=cites:<work_id>`**（实测返回 24,366 条）、`related_works`（算法相似推荐，非引用关系）；旧 `cited_by_api_url` 已不在官方属性字典，勿依赖；Crossref `reference[]` 可补充。

**存储**：sidecar 两张表起步
```sql
work(work_id TEXT PRIMARY KEY, doi, title, year, venue, cited_by_count, refreshed_at, ...)
citation_edge(src_work_id, dst_work_id, source, retrieved_at, PRIMARY KEY(src, dst, source))
```
节点身份统一 `work_id`；为已入库条目维护 `work_id ↔ itemKey` 映射即与本地库打通。

**四种算法（实现成本递增）**：① 向后引用链；② 向前被引链（找后续进展）；③ **主路径分析（main path analysis）**——学术谱系的标准做法，给出技术演进主线；④ 共被引 / 文献耦合聚类（识别流派）。
**可视化**：先出 **Mermaid / Graphviz**（零依赖、可入文档、diff 友好）；交互式图留待需要时。**大图必须裁剪**：数百节点以上人类读不动 → 路径裁剪 + 时间轴分层 + 每节点一句话摘要。
**成本**：引用边抓取属 `list+filter` 档（$0.10/千次），无 LLM 成本；被引 2 万条的节点要分页取样而非全量展开。

### 5.10 可信、合规与隐私

#### 5.10.1 "可信"的可执行定义

- 每条结论可落到 `{work_id/doi, itemKey, 页码或段落}`；无出处的断言不输出（写进 SKILL.md 硬规则，CLI 可加 `--require-citation` 强制）。
- 候选项携带来源与获取时间；原始响应留档。
- 质量信号进决策但不越权：闸门给"分级 + 理由"，取舍留给人或显式配置的策略。
- 已知缺陷显式暴露：DOI 与标题不一致、缺 DOI、venue 缺失 → 标记"元数据待核"，不静默采用。

#### 5.10.2 合规

- 只取 OA 版本；遵守各源条款：**arXiv 禁止自行托管/分发 PDF**；**PMC 只允许 E-utilities / OAI-PMH / BioC 等指定服务做自动化批量抓取**；Unpaywall 须真实 email。
- 翻译/摘要属派生使用，默认只对标题与摘要做，不整篇翻译再分发。

#### 5.10.3 隐私

本地库内容默认不出网；送往云端 LLM 的内容可枚举、可关闭；提供"全离线"档（本地嵌入 + 本地翻译模型），代价是质量与速度。

## 附录 A：sidecar 完整 schema

```sql
-- 0) 元信息：schema 版本与 Zotero 实例分区
meta(key TEXT PRIMARY KEY, value TEXT);   -- schema_version / zotero_server_id / data_dir

-- 1) 作品身份（主键 = OpenAlex Work ID）
work(work_id TEXT PRIMARY KEY,            -- 'W2626778328'
     title, year, venue, type, language,
     cited_by_count, fwci, is_retracted, oa_status,
     first_seen_at, refreshed_at, raw_json_path);

-- 2) 别名（一个作品可有多个 DOI / arXiv / PMID）
work_alias(work_id, id_type, id_value, source,
           PRIMARY KEY(id_type, id_value));
-- id_type ∈ {doi, arxiv, pmid, pmcid, openalex, title_key}
CREATE INDEX idx_alias_work ON work_alias(work_id);

-- 3) 与本地库的指针（唯一需要与 Zotero 对齐的表）
zotero_link(work_id PRIMARY KEY, library_id, item_key, server_id, linked_at, run_id);
CREATE UNIQUE INDEX idx_link_item ON zotero_link(library_id, item_key);

-- 4) 派生文本缓存（翻译/摘要）
derived_text(work_id, kind, lang, text,
             source_hash, model_id, prompt_version, glossary_version,
             created_at,
             PRIMARY KEY(work_id, kind, lang, model_id, prompt_version, glossary_version));
-- kind ∈ {title_zh, abstract_zh, summary_1line, summary_contrib, ...}

-- 5) 正文缓存元数据（正文本身在 blob 目录）
text_cache(content_hash TEXT PRIMARY KEY, work_id, zotero_attachment_key,
           blob_path, char_count, extractor, extractor_version, created_at);

-- 6) 引用边（未来脉络图）
citation_edge(src_work_id, dst_work_id, source, retrieved_at,
              PRIMARY KEY(src_work_id, dst_work_id, source));
CREATE INDEX idx_edge_dst ON citation_edge(dst_work_id);

-- 7) 候选池
candidate(work_id TEXT PRIMARY KEY, run_id, query, score, grade, reasons_json,
          status, staged_at, decided_at);
-- status ∈ {new, approved, rejected, promoted, skipped}

-- 8) 运行账本
run(run_id TEXT PRIMARY KEY, profile, started_at, finished_at, status,
    requests_used, cost_usd, new_candidates, deduped, promoted, error);

-- 9) 中文全文检索（trigram 支持中文；<3 字查询用 LIKE 兜底）
CREATE VIRTUAL TABLE derived_text_fts USING fts5(
    work_id UNINDEXED, kind UNINDEXED, text, tokenize='trigram');
-- 可选：先用 jieba 分词再写入 unicode61 索引，可支持 2 字词
```

**重建流程**（验证"sidecar 永不权威"）：删除 `.db` 与 blob → 从 Zotero 读条目与附件 → 重新抓取引用边与元数据 → 重算翻译/摘要（命中 LLM 缓存则零成本）→ 条目视图应与删除前一致。
