# 实验记录：全文文本化验证（M1.5 前置 spike）

> 实验日期：2026-10-14。目的：在写正式代码之前，验证 [03 设计说明书](03-设计说明书.md) §4.10「原生文本优先的全文文本化」是否成立，并把"想当然"的部分换成实测数字。
> 结论一句话：**路线可行，但 pandoc 必须配一层归一化（normalize）代码；单靠 pandoc 一条命令产出的 Markdown 是不能给 LLM 读的。**
> 路线选择一句话：**LaTeX 源码为主、arXiv HTML 为辅**——HTML 的体积、清洗、可用性都不成问题（§3.4、§3.5、§6.2），但它的数学里会出现**无法渲染的未展开自定义宏**（§3.3.1），这一条足以让它当不了主力。
> 复现脚本与产物：`data/spike-m1.5/`（8 篇论文源码 ~15 MB、中间产物 ~30 MB，共 45.6 MB；全部为 arXiv 原始文件，**不进版本库、不再分发**）。

## 2. 路线 A：arXiv LaTeX 源码 → Markdown

命令形态（最终采用）：

```
pandoc main.tex -f latex \
  -t commonmark_x+tex_math_dollars+pipe_tables+footnotes+implicit_figures \
  --wrap=none --citeproc --bibliography=<paper>.bib \
  --extract-media=<out>/_media
```
之后依次执行：公式归一化 → 图件归一化（含 PDF→PNG）→ 锚点注入 → 交叉引用解析 → 清理。

### 3.2 路线 B 的两个独有优势（实测）

1. **公式天生干净**。LaTeXML 输出的行间公式已经是 `$$\dot{\mathbf{y}}=f(t,\mathbf{y})+g(t,y_{1})\,u(t),$$`——**没有 `\begin{equation}` 外壳**。归一化统计里"未识别的原始 LaTeX 环境"路线 B 是 0~1，路线 A 是 5~84（见 §4.1）。
2. **图是 SVG，且表格有真实的表号表题**。LaTeXML 把 PDF 图转成了 SVG（矢量、无损）；`<figure class="ltx_table">` 里带着 `Table 1: …` 标签，路线 A 丢掉的表号表题在这里能拿回来。

### 3.3 路线 B 的代价（实测，按严重程度排序）

1. **自定义宏不展开（最严重，且只有路线 B 有）**。LaTeXML 把**宏调用**而不是展开结果写进 `annotation[encoding="application/x-tex"]`，pandoc 于是原样吐出来。以 `2610.18675` 为例（该文定义了 113 个宏）：

   | | 路线 A | 路线 B |
   |---|---|---|
   | 同一句话 | `$\mathbf{x}\in \mathbb{R}^n$` | `$\mathbf{x}\in\real^{n}$` |
   | 只在本路线出现的命令 | `\mathop`×27、`\text`×2（**都可渲染**） | `\real`×41、`\displaystyle`×15、`\sym`×11、`\tr`×8、`\range`×4、`\argmin`×4（**共 83 次未定义命令，渲染必失败**） |

   全样本统计：路线 A **0 处**未展开宏（8/8 篇全部展开正确）；路线 B 有 1/8 篇中招、共 64~83 处。原因是路线 A 让 pandoc 直接读 `\newcommand` 定义，宏在源头就展开了。
2. **体积 1.65 倍**（清洗后中位 107 KB vs 路线 A 65 KB；≈27k vs ≈17k tokens）。清洗砍掉 35% 后仍然更贵：LaTeXML 保留了完整参考文献表、脚注正文、章节导航残留。
3. **每个公式都被包在布局 `<table>` 里**。LaTeXML 用表格排公式编号，归一化阶段会被误判成真表格：路线 B 检出 25~282 个"表格"，而这些论文真实表格只有 0~14 个（`2610.18630`：检出 282，真实 0）。清洗能减半，但要彻底解决必须在进 pandoc 前把这些"单公式表格"拆掉。
4. **引用链接形态不同**，本 spike 的解析器**没有处理**：路线 B 产出的是 `[[1]](#bib.bib1)`（方括号套方括号），解析器针对的是路线 A 的 `[\[label\]](#label)`。因此路线 B 的"解析引用"计数为 0、未解析 39~85——**这是解析器覆盖不足，不是路线 B 的缺陷**。
5. **必须联网抓图**：图在 HTML 里是相对 URL，要逐个下载（路线 A 一个 e-print 包全拿到）。8 篇共 47 个资产、0 失败，但多了一次网络依赖。

### 3.4 清洗能省多少（-35%）

在 `<article>` 抽取之后、进 pandoc 之前做三件事：

1. 丢掉网页专用元素（`<nav>`、`.ltx_TOC`、脚注回链、作者块、`ltx_ERROR` 占位）；
2. 丢掉除 `id/href/src/alt/title/colspan/rowspan` 之外的所有属性（LaTeXML 的 class/style 极多）；
3. 把 `<span>` 拆包（class 没了之后它没有意义）。

**一个必须记住的坑**：**`<math>` 子树内一个属性都不能动**。第一次实现时统一剥属性，把 MathML 的 `display="block"`、`accent="true"`、`mathvariant` 一起删了，后果是①行间公式全塌成行内（`<!-- eq: -->` 锚点从 27~136 个掉到 0）②`\dot{x}` 退化成 `\overset{˙}{x}`（Unicode 组合点）。修正为"`<math>` 及其祖先链上的元素整体跳过"后，公式与原始路线完全一致（逐项 macro 计数相同），而体积反而更小：

| | 路线 B 原始 | 路线 B 清洗后 |
|---|---|---|
| 合计 paper.md | 1,596 KB | **1,040 KB（-35%）**，逐篇 -20%~-47% |
| 公式保真 | 基准 | **与原始完全相同**（`\dot`、`\mathbb`、`\mathcal`、`\boldsymbol` 计数逐项一致） |

## 4. 实测发现：单靠 pandoc 产出的 Markdown 不可用

这一节是本次实验最重要的产出。以下 6 个问题**全部 8 篇命中**，都不是边角情况。

### 4.1 问题 1：pandoc 不会解析 `\begin{equation}` 这类公式环境

- **现象**：pandoc 把 `\begin{equation}...\end{equation}` 整块塞进 `$$...$$` 里，连同 `\label{}`。产出形如 `$$\begin{equation}\label{sys:ctrl_affine} \dot x = ... \end{equation}$$`——这是**非法 LaTeX 数学**（`equation` 环境不能出现在数学模式内部），KaTeX/MathJax 会渲染失败。
- **规模**：路线 A 每篇 5~84 处（合计 267 处），`\label` 漏出 57~45 条。
- **处理**：写了一张"外层环境 → 数学模式内合法环境"的映射表（`equation` 拆壳；`align→aligned`、`gather→gathered`、`multline` 拆壳…），并把 `\label{}` 提出来变成锚点注释。处理之后"未识别原始环境"降到 0（`2610.18758` 剩 2 处未知环境）。
- **注意**：**这个坑与输出方言无关**，`gfm`、`markdown`、`commonmark_x` 全都一样踩。

### 4.2 问题 2：输出方言选错会直接毁掉公式（`-t gfm` 不可用）

同一篇 `2610.18675`、同一份源码，六种 `-t` 方言的实测：

| 方言 | 行间公式 | 行内公式 | 表格 | 图 |
|---|---|---|---|---|
| `gfm` / `gfm±tex_math_dollars` | ```` ```math ```` 围栏代码块（45 个），里面还是 `\begin{equation}` | `` $`x`$ ``（535 处，GitHub 代码跨度写法） | 管道表 ✓ | raw HTML |
| `commonmark_x+tex_math_dollars+pipe_tables+…` | **`$$...$$`** ✓ | **`$x$`** ✓ | 管道表 ✓ | raw HTML |
| `markdown+…+pipe_tables-grid_tables` | `$$...$$` ✓ | `$x$` ✓ | **丢表**（8 篇里 3 篇表格消失） | raw HTML |
| `markdown`（默认 grid 表） | `$$...$$` ✓ | `$x$` ✓ | 网格表（`+---+`） | raw HTML |

**结论：`-t gfm` 是错的选择**（把行间公式变成代码块、行内公式变成 `$`+反引号），**`markdown` 方言会丢表格**。固定用：

```
-t commonmark_x+tex_math_dollars+pipe_tables+footnotes+implicit_figures
```

### 4.3 问题 3：图件变成"带绝对路径的 raw HTML"

- **现象**：LaTeX 的 `\begin{figure}...\includegraphics{...}\end{figure}` 在**所有**方言里都输出为

  ```html
  <figure id="fig:hero" data-latex-placement="t">
  <figure id="fig:hero_closed_loop">
  <embed src="D:\...\out\_media/Figures/fig_hero_a.pdf" />
  <figcaption>End-effector paths</figcaption>
  </figure>
  ...（嵌套子图）
  <figcaption>长图注</figcaption>
  </figure>
  ```
- **三个毛病**：①不是 Markdown 图片语法，LLM 与阅读器都拿不到图；②`--extract-media` 传绝对路径时，**绝对路径被烤进文件**（换成相对路径才能随目录迁移）；③PDF 图用 `<embed>`，浏览器/Markdown 阅读器打不开。
- **处理**：用 `lxml` 解析每个 `<figure>` 块，抽出 `src` 与各级 `figcaption`，重写成

  ```markdown
  <!-- id:fig:hero -->
  <!-- fig: 1 -->
  ![End-effector paths](figures/fig_hero_a.png)
  <!-- fig: 2 -->
  ![Certified joint velocities at the outer boundary.](figures/fig_hero_b.png)

  *长图注*
  ```
  并把 PDF 用 `pdftocairo -png -r 200 -singlefile` 转成 PNG。**47 张图 0 失败**。

### 4.4 问题 4：引用与交叉引用必须显式处理

- **不处理会怎样**：`\cite{ong2026matrix}` 会变成 `` `\cite{ong2026matrix}`{=latex} `` 这种 raw inline（属性语法漏进正文），或干脆被丢弃；`\cref{eq:safe_set}` 变成 `[\[eq:safe_set\]](#eq:safe_set)`——LLM 看到的是**标签名而不是编号**。
- **处理**：①`--citeproc --bibliography=<paper>.bib` → 引用展开为 `(Ong et al. 2026)`、`(Zeng et al. 2021; Gurriet et al. 2020)`，并自动附上参考文献表；②在归一化阶段顺手收集 `label → 编号` 表（公式/图/表/章节/定理环境），把 `[\[label\]](#label)` 改写成 `[eq. 2](#eq:safe_set)`、`[Fig. 1](#fig:hero)`、`[Definition 2](#def:MCBF)`。
- **效果**：路线 A **691 条链接被正确改写，76 条未解析（约 90% 覆盖率）**，且改写完全靠锚点表，没有猜。

### 4.5 问题 5：arXiv HTML 的图是 `<object data="...svg">`，不是 `<img>`

- **现象**：`2610.18361` 的 article 里 `<img>` 0 个、`<object>` 6 个；`2610.18311` 是 0 个 / 8 个。按 `<img>` 找图会一张都找不到。
- **处理**：同时处理 `<img>`、`<object data>`、`<embed src>`；并把 `<object>` 转成 `<img>`（pandoc 的 HTML reader 不把 `<object>` 当图片）。
- **另一个坑**：图地址是相对于 **HTML 目录**的（`2610.17929v1/figures/x.png`），正确前缀是 `https://arxiv.org/html/`（**不再拼一次 id**）。拼错就是 404（本次先踩了一次）。

### 4.6 问题 6：Windows 上的两类自伤

| 现象 | 原因 | 对策 |
|---|---|---|
| 正则 `^\|.*\|$` 匹配不到任何表格行 | pandoc 在 Windows 输出 **CRLF**，`$` 前多一个 `\r` | 读入后立刻 `replace("\r\n", "\n")` |
| 全文 HTML 转出的 Markdown 里行间公式粘连正文（`$$ where ...`） | 源文件里公式与后文在同一段（`\end{equation} where ...`），pandoc 只换一段 | 归一化时**所有**行间公式一律重排成独立块：`\n\n$$\n…\n$$\n\n` |

另有两条工程细节：①用 PowerShell here-string 里跑 `python -c` 会把 `$E=mc^2$` 当变量吃掉——**脚本一律写成 `.py` 文件**；②pandoc 的 `\textsc{}`、`\underaccent{}` 等宏无法转数学（`2610.18361` 9 处、`2610.18675` 1 处），pandoc 会**保留原始 LaTeX**并给 WARNING——内容不丢，但 KaTeX 渲染不了，属于已知可接受损失。

## 6. 成本与预算数据（可直接用于容量规划）

### 6.1 上下文成本（这是真正的约束）

| 指标 | 路线 A（LaTeX 源码） | 路线 B（HTML，清洗后） | 路线 B（HTML，未清洗） |
|---|---|---|---|
| 单篇 `paper.md` | 47–134 KB（中位 **65 KB**） | 86–207 KB（中位 **107 KB**） | 117–391 KB（中位 160 KB） |
| 单篇 ≈ tokens | **12k–34k（中位 ≈17k）** | 22k–53k（中位 ≈27k） | 30k–100k（中位 ≈40k） |
| 单篇图件 | 2–10 张 PNG，8 篇共 3.9 MB | 2–16 张（多为 SVG），8 篇共 6.1 MB | 同左 |
| 转换耗时 | **0.20–0.40 s** | 0.30–0.68 s | 0.33–0.84 s（含图下载） |
| 计算资源 | 纯 CPU，无模型、无 GPU | 纯 CPU + 图件 HTTP 下载 | 同左 |

**给"精读一篇论文"的预算**：路线 A 一篇 ≈ **17k tokens**（中位），8 篇 ≈ 166k tokens。一次会话精读 1~2 篇全文 + 若干篇摘要完全可行；也说明缓存（翻译、摘要、文本化结果）值得做——省的是**重复转换与重复上传**，不是算力。

**路由选择的上下文账**：按"一次会话 128k 上下文、需要留一半给推理"算，路线 A 一轮能读 ~3 篇，路线 B 清洗后 ~2 篇。差距不大但真实存在；真正压倒性的差别是 §3.3 的宏展开问题。

### 6.2 磁盘占用（实测，8 篇合计）

| | 论文源码/HTML | paper.md | 图件 | **单篇合计** | 1,000 篇外推 |
|---|---|---|---|---|---|
| 路线 A | 10.3 MB（e-print，158–693 KB/篇） | 651 KB | 3.9 MB | 250–999 KB（中位 ~500 KB） | **≈0.5 GB** |
| 路线 B 未清洗 | （同一份 HTML 368–973 KB/篇） | 1,596 KB | 6.1 MB | 419–2,085 KB（中位 ~600 KB） | ≈0.6 GB |

## 7. 遗留问题（下次动手前要处理的清单）

1. **引用解析器补齐三种形态**：路线 B 的 `[[1]](#bib.bib1)`；`algorithm2e` 伪代码块（`alg:*`）；`assumption`/`lemma` 等未生成 id 的 div。

4. **HTML 路线的清洗仍未做完**：§3.4 那一轮已经省了 35%，但"每个公式被包在布局 `<table>` 里"这条还没解决（检出 25~282 个伪表格，真表格只有 0~14 个）。需要在进 pandoc 前识别并拆掉这类单公式表格。
5. **HTML 路线的自定义宏需要在进 pandoc 前展开**：若将来真要把 HTML 当主路线，必须先从 LaTeX 源码取 `\newcommand` 表并做宏替换，否则 `\real^{n}` 这类命令会一直漏出来。这是本记录不建议 HTML 当主力的首要原因。

8. **未测中文论文、扫描件与非 arXiv 来源**：本批样本全是英文 arXiv 论文；PDF→MD 与 OCR 回退层（pymupdf4llm 已在本机）完全没有进入测试范围。另外**非 arXiv 的出版社 HTML（MDPI/IEEE/Elsevier）结构完全不同**，本次的 LaTeXML 清洗逻辑不能直接复用，需要各写各的——这是"HTML 当家"在跨来源场景下的另一个坑。
9. **HTML 路线有少量内联 base64 图**：LaTeXML 会把图内的小图形嵌成 `data:image/svg+xml;base64,…`。实测 8 篇中只有 2 篇命中（`2610.18361` 1 处 1.6 KB、`2610.18758` 6 处 74.5 KB，占该篇 19%）。清理时应把内联 base64 落盘成独立 SVG 文件，而不是留在 Markdown 里。

### 8.2 arXiv → OpenAlex 的可构造桥（本机实测）

`10.48550/arXiv.<arXiv-id>` 是 arXiv 自己注册的 DataCite DOI，**可以直接拼出来**，实测覆盖 2006（含 `math/0601001` 老式 id）到**当天发布**的论文。因此 `filter=doi:10.48550/arXiv.<id>` 是零构造成本的入口（$0.0001/次）。三个反例要记住：

- **Crossref 不认识它**（实测 404）——预印本不能靠 Crossref 桥接；
- **arXiv API 的 `<arxiv:doi>` 是作者手填的**（实测 3 篇中仅 1 篇有）；
- **有已知错配**（[02 §3.5](02-现状与调研.md) 第 3 条：`10.48550/arXiv.2210.03629` 返回的是另一篇论文）→ 命中后必须校验标题/年份。

唯一**显式给出** arXiv 映射的是 Semantic Scholar：`GET /graph/v1/paper/arXiv:<id>` 无 key 返回 `externalIds = {MAG, ArXiv, DBLP, DOI, CorpusId}`（免费，但共享池实测**第一发就 429**）。

### 8.3 标题能不能当身份：三次实测（脚本 `16`、`17`、`19`）

> **先澄清问题**：本节回答的是「把标题转小写（+去标点）后算哈希、拿这个哈希当 `uid` 行不行」，**不是**"能不能用标题上网找回论文"。后者是实验 A，只作旁证；决定性问题由实验 C、B 回答。

**实验 C — 在本领域真实语料里，`hash(小写标题)` 会撞多少次**（arXiv `eess.SY` 最近 **10000** 篇，免费 API 分页拉取）：

| 指标 | 值 |
|---|---|
| 记录数 | 10,000 |
| 不同标题 key | 9,997 |
| 撞车组 | **3 组（6 条记录，0.06%）** |
| 逐组内容 | 3 组**全部是同一作者、同一标题的重复投稿**（如 `2604.18810v1` / `2604.18814v1`），**没有出现"两篇不同论文同名"** |

→ **单看碰撞率，`hash(title.lower())` 在本领域的论文语料里"够用"（0.06%）。** 所以"不可行"的理由不在碰撞率，而在 §8.5 的三条结构性冲突。

**实验 B — 一旦跨来源，碰撞率立刻跳两个数量级**（12 个泛化控制类标题、719 条真实 Crossref 记录，**故意取最坏情况**）：

| 判据 | 撞车记录 | 最大一组（不同 DOI 数） |
|---|---|---|
| ① `title_key`（宽松归一化） | **115/719 = 16%** | **7 篇** |
| ①' `title_key`（严格归一化，不砍副标题） | 104/719 = 14% | 7 篇 |
| ② `title_key` + 年份 | **27/719 = 4%** | 3 篇 |
| ③ `title_key` + 一作姓氏 | 87/719 = 12% | 5 篇 |
| ④ `title_key` + 一作姓氏 + 年份 | 27/719 = 4% | 3 篇 |
| ⑤ ④ 但年份放宽到两年一组 | 35/719 = 5% | 4 篇 |

两个可操作的读数：

- **年份是判别力最强的单字段**（16% → 4%）；一作姓氏单独加几乎没用（16% → 12%），但它是"④ 与 ② 打平"的必要组成。
- ④ 仍撞车的例子暴露了一类脏数据：`Front Matter`（2 本不同的书）、`Index`（**3 本不同的书**）——**书章节/前言/索引这类记录标题本身就重复**，需要按 `type` 过滤或加黑名单。

**实验 D — 反方向：同一篇论文的标题在预印本与正式版之间会变多少**（脚本 `21_title_drift.py`）。取 eess.SY 最近 2000 篇中**作者手填了期刊 DOI** 的 115 篇（占 **6%**），逐个到 Crossref 取正式版标题对比，28 篇可解析：

| 差异程度 | 篇数 | 例子 |
|---|---|---|
| **完全相同** | 19/28 = 68% | — |
| **只有大小写/标点** | 6/28 = 21% | `…with Grid Topology` → `…With Grid Topology`；`Student-Teacher` → `Student–Teacher`（连字符变 en dash） |
| **实质不同** | **3/28 = 11%** | ① `Deep learning from a control vantage point` → `Deep Learning From a Control Vantage Point: Feedforward, Residual, Transformers, Large L…`（**补了副标题**，Jaccard 0.41）② `Modelling` → `Modeling`（**英式/美式拼写**，Jaccard 0.88）③ `An $\mathcal{L}_1$ Adaptive Optimizer Approach` → `An L <sub>1</sub> Adaptive…`（**数学变 HTML 下标**） |

→ **约 1/3 的论文在预印本与正式版之间标题字符串不同，其中 11% 是任何大小写/标点归一化都救不回来的实质差异。**

**归一化强度是一个跷跷板**：归一化弱（保留副标题）→ 实验 D 恶化；归一化强（砍副标题、砍标点）→ 实验 B 恶化（碰撞 14% → 16%，实测）。**两个方向对同一个旋钮的要求相反，不存在能同时压到零的归一化强度。这是结构性缺陷，不是调参问题。**

**结论**：`title_key` **只能当召回键（blocking key），不能当 uid，也不能进唯一约束**。判据用 `title_key + 一作姓氏 + 年份(±1)`，并追加一条否决条件——**两边的强标识（DOI/OpenAlex/arXiv）互不冲突时才允许自动合并**。

### 8.5 备选方案：随机 id（**当前不采用**）

> **当前采用的不是这一套。** 正式设计（[03 D3](03-设计说明书.md)、[04 决策 L](04-实施计划与决策.md)）是**确定性身份**：`record_uid = base32(sha256(source ‖ source_id))[:20]` 由来源坐标派生，`work_key` 直接取组内最早记录的那个 `record_uid`——**全库没有随机铸造的标识符**。
>
> **随机 id 的致命性质是"不可复现"**：两台机器各自导入同一批来源会得到不同的 id、不同的 `blobs/` 路径，删库重建后也对不上，导出文件无从比对。它唯一的好处是把 work 与 record 在概念上彻底解耦，而当前需求用不到这种解耦。
>
> 下面记录的是**如果将来真需要随机 id**时实测得到的格式与正确性结论（脚本 `18_uid_minting.py`，stdlib 实现已跑通）——包括一个会破坏单调性的实现坑，可直接复用。

**格式：ULID，26 字符，Crockford base32**

```
01M4X4YHMJC1PV5PSDCAD23F53
|--------||--------------|
 48 位毫秒    80 位随机
```

实测性质（同毫秒连铸 10,000 个）：长度恒为 26；字符集去掉 `I/L/O/U`（不会看错）；**全部唯一**；**字典序 == 生成序**（可直接当目录名前缀与查询排序键）；时间戳可反解；可直接 `mkdir` 当目录名。

> 踩过的坑：本实现最初把 80 位拆成「16 位计数器 + 64 位随机」，计数器回绕后单调性崩了（"字典序 == 生成序"变 False）。按 ULID 规范改成**把整个 80 位当整数递增、溢出则时间戳 +1ms** 才正确。

**规则（policy，比格式更重要；均针对随机铸造方案）**：

1. **只有一处铸造**：一个 `resolve_or_mint()` 入口。代码库其它地方不得构造 uid；DB 也不要用 `randomblob()` 之类的默认值——那会绕过唯一入口。
2. **铸造时机**：一篇作品首次出现、且**所有强别名都未命中**时。
3. **铸一次，终身不变**：不重铸、**不从内容算**（这与最终采用的确定性方案相反，是随机方案的根本弱点：一旦需要重算，值必然改变）。
4. **不带语义**：不加 `oa:`/`doi:` 前缀、不嵌日期、不嵌标题片段。id 里一旦有语义，就会有人想"重算"它——而重算必然改变它（当天 arXiv 论文只有 `ax:`，两天后才有 `oa:`）。
5. **幂等靠唯一约束**：把 `(ns, value)` 之类的强标识放进 `PRIMARY KEY`，让"先插后查"天然幂等——`INSERT ... ON CONFLICT DO NOTHING`，冲突即代表已存在。（最终方案里这张表叫 `record_ident`，见 [03 附录 A](03-设计说明书.md)。）

**为什么 `hash(小写标题)` 不能当 uid**（以下对**任何**身份方案都成立，含最终采用的确定性方案）：

1. **哈希不改变碰撞行为**：`hash(x)` 在 `x` 相同时必然相同，截断只会**增加**碰撞。所以「小写后哈希」=「小写」的碰撞率 + 截断风险；哈希在这里不提供任何分散能力。
2. **标题是"记录"的属性，不是"作品"的属性 → 两个方向都会错**：同一作品在不同来源/版本标题不同（大小写、副标题、嵌入标记）→ **一个作品两个 uid**；不同记录标题天然重复（`Index`/`Front Matter`）→ **两个作品一个 uid**。跨来源时碰撞率从 0.06% 跳到 16%。
3. **身份键必须"一次定终身、永不变"，而标题会变**。`record_uid` 一旦写进 `blobs/<…>/`、缓存键、导出文件、Zotero 链接就改不动了。**这不是概率问题，是语义不匹配。**（随机方案那条"铸一次、终身不变"的规则，根子也在这里。）
4. 附带一条代价不对称性：**漏判**（同一篇两个 uid）只是浪费、可合并；**误判**（两篇共用一个 uid）会让它们的 `paper.md`、图件、翻译、笔记、引用边**互相静默覆盖**。身份键不能用"概率上够用"的东西。

**正确用法**：`title_key` 保留，作**召回键**；而且**不必哈希**——存规范化字符串更便于人工核对。真正该哈希的是**文件字节**（内容哈希），且只用于缓存失效，不参与身份。
