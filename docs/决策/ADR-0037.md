# ADR-0037　翻译与摘要由对话中的同一模型经子 agent 产出；CLI 不直接调 LLM

**状态**：accepted（2026-10-15）

- **决策**：初版**不给 CLI 接任何 LLM API**。翻译与摘要通过一对命令由 agent 完成：

  ```
  digest list --limit N     # 输出待处理的 (work_key, kind, lang, 源文本)，按缓存键去重
  digest put  --work <key> --kind <k> --lang <l> --model <id> --prompt <ver>   # 收 agent 产出的文本
  ```

  `SKILL.md` 负责串起这两步；`model_id` / `prompt_version` 照常记录，因此将来换成专用模型时缓存键自然区分，历史缓存不会被误命中。

- **理由**：
  1. **零额外成本**：用对话里已经付过费的那次推理，不需要 API key、不需要额度管理，也不需要 `Batch API` 与"超限降级"这套逻辑。
  2. **确定性与可测性**：CLI 保持"无网络、无密钥、可重放"，翻译质量的问题不会混进工具本身的故障里。
  3. **隐私默认最好**：内容不出本机——除对话本身之外不新增外发通道（[REQ N3](../01-需求说明.md)）。
  4. **与 [ADR-0035](ADR-0035.md) 同构**：翻译也是**按需**发生——定时 run 只落候选，翻译发生在有人真的要看的时候。

- **代价**：
  1. **定时 run 无法自动翻译**：无人值守的 `sync` 只落候选与元数据，中文摘要要等下一次交互才补齐。这不违反 [ADR-0030](ADR-0030.md)——那条讲的是"要不要人工确认"，不是"谁调用模型"。
  2. **批量翻译会吃对话上下文**：靠 `--limit` 限流，一次处理一批。
  3. 翻译质量取决于对话模型的当前档位，且**不经术语表强制注入**——术语一致性靠 `glossary_version` 与提示词，不靠模型侧词表。

- **计划内后续**：专用翻译模型（本地或云端）是**计划内范围**，不是被否决的方案。触发条件：① 批量翻译需求超出对话上下文的承受度；② 术语一致性成为硬要求；③ 需要无人值守产出中文摘要。届时 CLI 增加一条"直连模型"的通道，与 `digest list/put` **并存**——两者写同一张 `derived_content`，靠 `model_id` 区分，缓存互不污染。
