# ADR-0043　检索只有一条路径：刷新（可选）→ 查库 → 返回；`--refresh` 管的就是「刷不刷」

**状态**：accepted（2026-10-15）

> **取代**：本条决策 4 中"定时任务刚跑过的具名查询，在对话里再查会命中并跳过"里的"再查"由 [ADR-0049](ADR-0049.md) 取代——具名查询在会话里重跑要走 `sync`；`spec_hash` 账本判据不变。

- **决策**：
  1. **检索只有一条路径**：`刷新（可选）→ 查库 → 返回`。网络检索的结果**先落库**（`record` + `candidate`，[ADR-0011](ADR-0011.md)、[ADR-0007](ADR-0007.md)）；**查询永远只面对数据库**。因此不存在「本地结果」与「网络结果」两张表要合并——网络结果落进来之后就是同一张表里的行。
  2. **取消 `--scope`，换成 `--refresh auto|true|false`**：既然永远只查库，唯一要决定的就是「刷新这一步做不做」。**三个值都必须显式给出，不支持裸写**——「裸写 `--refresh`」与「省略 `--refresh`」行为不同，而这种差异只会在文档里制造误读。

     | 值 | 行为 |
     |---|---|
     | `auto`（默认） | **自行判断**：见决策 3；跳过时**在输出里明确标注「已跳过刷新，上次于 X」** |
     | `true` | 强制先刷新，再查库 |
     | `false` | **绝不联网**，只查库（硬保证，离线可用） |

  3. **`auto` 的判据：每个检索式各记各的时间**。键是 `spec_hash = sha256(规范化后的检索式)`（字段排序、大小写归一、**关键词排序**——顺序无关）。

     | 情况 | 行为 |
     |---|---|
     | 该 `spec_hash` **从没刷新过** | **必须刷新**（新方向第一次一定联网） |
     | 有记录且 `now - at ≤ max_age_hours` | 跳过并标注 |
     | 有记录但超时，或**检索式不等价** | 刷新 |

     **方向是「宁可多花一次，不可漏」**：不等价一律刷新，绝不近似匹配。
  4. **状态存在 run 账本里，不新建表**：`run` 增加 `spec_hash` 与 `refreshed` 两列。`search` 与 `sync` 共用同一账本，因此**定时任务刚跑过的具名查询，在对话里再查会命中并跳过**。
  5. **阈值**：默认 **24 小时**（与 arXiv「每天更新一次」的节奏对齐），可被 `config/search.toml` 覆盖，也可被 `--max-age <时长>` 单次覆盖。
  6. **来源标在数据里**：每条结果带 `first_seen`（首次入池时间）。要只看新的，筛它即可——**「新旧」是行的属性，不是开关**。
  7. **联网与花费必须可见**：输出信封带 `network`（本次是否刷新过）与 `cost`（花费及口径）。
  8. **`search` 与 `lookup` 的刷新语义不同**：`lookup` 按标识取，**命中即返回**（标识确定，「外面有没有新的」对它不成立）；`search` 是发现式，`auto` 档会按新鲜度刷新。

- **理由**：
  1. **「两边都查再合并」是个伪问题**：联网结果本来就必须落库（否则幂等与去重都不成立），落完之后它与既有行同处一表。把架构说成「两个来源合并」，会让人以为存在一个不落库的临时层——而那正是 [ADR-0007](ADR-0007.md) 要消除的分叉。
  2. **`--scope` 已经名不副实**：初版没有「我的库」，`local` 与 `corpus` 无区别；而「查哪里」也不是真问题——只有一张表可查。真正的选择是「要不要花钱刷新」。
  3. **判据按检索式各记各的，不是所有检索式共用一个全局时间**：全局量在**混合刷新**下会互相干扰——定时任务 09:00 跑过 A 方向、你 10:00 临时查了 B，全局时间就被 B 刷新成 10:00；此时该跑的 C 会被判成「刚同步过」而跳过。各自记时间就没有这个问题。**「从未出现过的检索式必须刷新」是这套判据的自然结果**：查不到记录就是没刷过，不需要单独一条规则。
  4. **不等价就不跳过**：`auto` 是省钱优化，不是正确性机制。近似匹配（比如"看起来差不多的关键词就复用"）会把漏检伪装成省钱，而多刷一次的代价只有 $0.001 量级。
  5. **`auto` 不是隐藏行为**：它是默认档，但**每次跳过都会在输出里说出来**。用户看得见「这次没刷新，因为 3 小时前刚查过」，就不会有「我明明要最新的却没联网」的困惑。

- **代价**：
  1. **临时检索的 `auto` 收益取决于措辞是否稳定**：agent 换个说法就是新 `spec_hash`，会再刷一次（多花 $0.001，不会漏）。因此 `auto` 的收益集中在**具名查询**上——名字与内容都固定。这又多了一条「用定时任务跑具名查询」的理由。
  2. **默认 24 小时是估计值，不是实测**：实测只证明 arXiv 每天午夜更新一次、OpenAlex 收录滞后 > 1.5 天。24 小时与前者对齐、更省请求，代价是**最坏延迟约等于阈值**（刷新点若刚好落在批次发布之后，下一次要等到阈值满）；具体数字待 M1 跑通后按真实节奏校准。
  3. 规范化规则若日后调整（比如改成词干归一），旧 `spec_hash` 会全部失配——表现为「都刷新一次」，不会漏，但要多花一轮钱。
  4. 早期文档里的 `--scope` 引用要一并同步（已在本轮完成）。

- **备选方案（当前不采用）**：
  - **`--scope local|all`（二值，管「查哪里」）**：不采用的理由见理由 2——它回答的不是真问题。
  - **`auto` = 本地命中不足 `--limit` 才联网**：不采用的理由——它把「本地命中数」当成「外面有没有新的」的代理，而两者无关；实际效果是**该联网时不联网**。
  - **不做 `auto`，只暴露 `last_net_at` 让 agent 自己判断**：不采用的理由——agent 必须在**调用前**就知道上次刷新时间才能决定，而那需要额外一次往返；把它做成一档更省。
  - **所有检索式共用一个「上次刷新时间」**（而非按 `spec_hash` 各记各的）：不采用的理由见理由 3——它在混合刷新下会把该跑的检索式判成「刚同步过」而跳过。注意这与「按时间阈值判断」无关：**阈值判据本身是采用的**，被否的只是「共用一个时间」。
