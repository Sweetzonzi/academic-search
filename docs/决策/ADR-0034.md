# ADR-0034　`works/` 用硬链接指向 `bytes/`，且 `bytes/` 里的文件设只读

**状态**：accepted（2026-10-15）

- **决策**：`works/<work_key>/` 下的每个文件都是 `bytes/<sha 前2位>/<sha256>` 的**硬链接**（不是副本，也不是符号链接）；`bytes/` 里每个文件在写完并校验 `sha256` 之后**设为只读**。

- **实测依据**（本机 NTFS，同一卷）：

  | | 副本 | 硬链接 | 符号链接 |
  |---|---|---|---|
  | 磁盘占用 | 2× | **1×** | 1× + 一个链接文件 |
  | 经 `works/` 路径改写，`bytes/` 是否被污染 | 不会 | **会** | **会** |
  | `tar` 打包 | 打进真字节 | 打进真字节 | **打进 0 字节的链接，且目标写成本机绝对路径** |
  | 跨卷 | 可以 | **不可以** | 可以 |
  | Windows 创建权限 | 无 | 无 | **需开发者模式或管理员** |

- **理由**：
  1. **副本让内容寻址的初衷落空**：`bytes/` 省下的重复空间会在投影层原样还回去——副本是三个选项里唯一「两头亏」的（比硬链接多占一倍，比合并成一层多一份复杂度）。而跨作品共享的字节（同一份源码支撑预印本与正式版两条记录）正是 `bytes/` 存在的理由。
  2. **只读属性是 inode 级的，硬链接自动继承**：给 `bytes/` 里的文件设只读，`works/` 下所有指向它的名字跟着只读。实测经 `works/` 路径追加或覆盖都返回 `EPERM`，`bytes/` 内容不变。编辑器只会提示「文件只读，另存为？」——**「要改就复制走」因此是默认行为，不靠自觉**。
  3. **符号链接不能用于打包与分发**：`tar` 存下的是链接本身（0 字节）且指向本机绝对路径，包发给同学链接全断并泄露本机路径；Windows 上创建符号链接默认还要开发者模式。
  4. **硬链接下 `works/` 不占额外空间**，「取消它以省空间」的动机不存在，因此保留这一层的四个收益（可预测路径、相对引用、整体打包、可浏览）都是免费的。

- **代价与约束**：
  1. **不能跨卷**：`bytes/` 与 `works/` 必须在同一个盘。启动时校验，不满足即报错。
  2. **只读不是物理保证**：从 `works/` 侧 `chmod` 去掉只读后仍可写穿到 `bytes/`（实测可以），届时 `bytes/` 的文件名与内容不再匹配——后续写入会因为「文件已存在」而跳过，继续使用被改过的内容，**属静默损坏**。缓解：① 默认只读；② 提供 `verify` 命令抽样重算 `sha256`。
  3. **清理顺序**：Windows 上删除只读文件需先 `chmod`；删 `works/` 不释放空间（`bytes/` 仍持有引用），GC 必须按引用计数走。
  4. **文件系统支持探测**：网络盘或某些文件系统不支持硬链接，启动时探测，不支持则降级为副本并告警。
