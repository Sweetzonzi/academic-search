# ADR-0045　面向阅读的派生文本进 `bytes/`，sidecar 只留缓存键与指针

**状态**：accepted（2026-10-15）

- **决策**：
  1. **判据**：**能被 SQL 当条件、排序或分页用的字段留在 sidecar；产出的文本一律进 `bytes/`。**
  2. 按此，**翻译与中文摘要的文本进 `bytes/`**（内容寻址），sidecar 的 `derived_content` 退化为**缓存键与指针表**——组合键 `(content_hash, kind, lang, model_id, prompt_version, glossary_version)` + `sha256`，**`text` 列清空**。
  3. **DB 只保留源文本**：标题与摘要原文留在 sidecar——它是 FTS5 的索引源，也是重译、校验与 `content_hash` 的输入。
  4. **FTS5 只索引英文原文**（标题、摘要）；翻译与中文摘要一律不进索引（承 [ADR-0042](ADR-0042.md)）。检索由 LLM 用英文发起。
  5. **"缺不缺"的判定走指针行**：`digest list` 用 `LEFT JOIN` 加 `LIMIT` 找出尚未生成的条目，**不靠文件系统探测**；文本只在读取展示时才从 `bytes/` 读出。
- **理由**：
  1. **与全文同构**：全文类产物早已是"字节进 `bytes/`、sidecar 只存指针"（[ADR-0029](ADR-0029.md)、[ADR-0033](ADR-0033.md)）。短派生文本是同一类东西——只是恰好短——两套规则并存会一直需要解释。
  2. **LLM 不需要译文**：检索一律英文，翻译只面向人（[ADR-0042](ADR-0042.md)）。译文进 DB 换不到任何查询能力。
  3. **指针必须留**：列出待处理条目、限流与分页都是 SQL 的联接与 `LIMIT`；连行都不留就得对每个候选探测文件，且无法排序分页，会破坏"查询只有一个入口"（[DESIGN §4.3.1](../02-设计说明书.md)）。
  4. **权属清晰**：译文是**可重算的派生数据**，删掉重跑即可；`bytes/` 的只读与内容寻址正好表达这一点（[ADR-0034](ADR-0034.md)）。

- **否决**：
  - **译文留在 `derived_content.text`**：DB 从索引退化为文本仓库，膨胀与备份代价随语料线性增长，且与全文的处理不一致；
  - **文本与指针都进文件**：失去"按内容哈希复用"与"缺哪一个"的 SQL 能力；
  - **原始摘要也不进 DB**：它是 FTS5 的索引源与 `content_hash` 的原像，移出去会让检索与校验都无处落地。

- **代价**：
  1. **小文件数量**：领域语料 10³–10⁵ 量级，译文与摘要按 kind / 语言 / 版本各一份，会产生大量约 1 KB 的文件；按 `sha` 前两位分片后每目录数百个，可接受，但实现时要确认目录操作性能。
  2. **列表展示要读文件**（可缓存）；`digest list` 的条目多起来后，逐条读的 I/O 需要批量化。
  3. **日后要开中文检索时多一步显式导入**：译文在 `bytes/` 里，`trigram` 表需要从文件批量灌入（[ADR-0042](ADR-0042.md) 的回退路径）；文件形态不阻碍这件事，但它不再是同库内的就地建表。
  4. **`derived_content` 与 `artifact` 的分工要写进实现**：前者回答"这段原文配这组参数算过没有"（跨 work 共享），后者回答"这份产物来自哪条记录"（记录级溯源）；两表并存，须在 DDL 处注明各自唯一键。
