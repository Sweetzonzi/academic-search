# ADR-0070　本地候选预算与 `counts.local`

**状态**：accepted（2026-10-19）

> **范围**：本条只改「FTS 命中之后、展示之前」这一段——候选取多少、结构化过滤在哪一层生效、以及载荷怎么交代。`--limit` 仍是**只截断展示**（[ADR-0062](ADR-0062.md)）；远端仍只取一页 100 条；`--venue` 的载体判据本身不变（[ADR-0060](ADR-0060.md)）。

- **决策**：

  1. **候选预算取代硬编码 500**：`config/search.toml` 的 `[local] max_candidates`，默认 `5000` 条记录、`0` 或负数 = 不限（[配置](../使用/配置.md)）。预算用尽时 `counts.local.truncated = true`。
  2. **结构化过滤进同一条 FTS SQL**：`status` / `--source` / 日期窗写在 `WHERE` 里、在 `LIMIT` **之前**生效；不再「先取 500 条、再按记录过滤」。
  3. **`counts.local` 恒出现**（离线也有）：`{considered, matched, returned, truncated, venue_filtered_out}`。
     - `considered`：候选预算内的 work 数（去重后）；
     - `matched`：过了 venue / 作者 / 阈值 / 撤稿之后、`--limit` 之前的 work 数；
     - `returned`：实际返回的条数；
     - `truncated`：预算是否用尽（`true` 表示「可能还有没看的匹配」，不是「结果就这么多」）；
     - `venue_filtered_out`：文本命中但载体集合不含白名单的 work 数（只在给了 `--venue` 时有意义）。
  4. **不做「不够 `--limit` 就翻下一页 501–1000 再合并」作为主方案**：它只在「过滤很挑、结果不足」时有用，救不了「结果够但排序取错」（见理由 2）。若将来要做，终止条件必须是「候选耗尽或预算耗尽」，不能是「凑够 limit」。

- **理由**：

  1. **500 条硬上限是静默的漏召**。实测本机库（4497 条记录 / 4131 个 work），`--all-of "world model" --venue NeurIPS`：cap 500 → 51 个 work，cap 1000 → 75，放开 → 99。硬上限在任何文档里都没有名字，用户只会看到「少了一半」。
  2. **相关性排序与展示排序不同序**。FTS 按 bm25 取候选，展示按 `published_at` 或 `cited_by_count` 排。cap 500 时 `--sort citations --limit 20` 的 top20 与全量 top20 **只重合 10 条**，而且**被引最高的那篇（226 引）根本不在结果里**——此时 `matched=51 > limit=20`，「没到 limit 才翻页」根本不会触发。翻页能救「0 条 vs 1 条」那种不足，救不了这种取错。
  3. **成本上 500 省不了什么**。同一查询：cap 500 约 47 ms、cap 1000 约 80 ms、全量（1338 个 work）约 112 ms。为了 60 ms 丢掉近一半命中，不划算；真正要优化时该优化的是「每个 work 5–6 条 SQL」的 N+1，而不是少看一点。
  4. **过滤下推是免费的**：`status` / `source` / 日期窗本来就在同一条记录上，放进 FTS 的 `JOIN` 后，预算只被**已经合格**的记录占用；同一预算能多回收一截。
  5. **`counts` 必须能解释「为什么变少」**。此前 `counts` 只有远端取数与入库数（`by_source` / `new_candidates`），而本地检索是**全库**过滤、不是从这批取数里筛；用户把「取 100」与「回 14」对起来看，只能得出「漏了 86 条」这个错误结论。

- **否决**：

  1. **保留 500、只在文档里写一句**：漏召仍然发生，而且「带 venue 的查询少一半」正是最需要准确的场景。
  2. **「不足 limit 就翻页」当主方案**：见理由 2；它还会把「候选上限」变成「按需翻页」，终止条件依赖展示排序，实现更绕、结果仍是近似。
  3. **一步到位改成 SQL `GROUP BY work_key ... ORDER BY ... LIMIT`**：方向对，但 `work` 表目前只有 `work_key` 与 `merged_into`，work 级聚合（最大被引、最早日期、载体并集）要物化一张 `work_summary`，属于 schema v5。先用预算 + 下推拿到正确性，等规模真的上来再做。
  4. **把 `counts` 拆成 `fetched / matched_local / dropped`**：`matched_local` 是在全库上算的，与 `fetched` 没有减法关系；这个形状会固化一个错误的流水线模型。

- **代价**：

  1. **宽泛查询变慢**：全量扫描随 work 数线性增长（本机约 0.08 ms/work）。3 万个 work 约 2.5 秒——到那一步再做决策 3 的物化。
  2. **载荷变大**：`counts.local` 多五个数字，离线查询也开始带 `counts`。这是有意的：离线正是最需要解释「为什么只有这些」的时候。
  3. **`venue_filtered_out` 可能与用户的直觉不符**：它包含「文本命中但只有预印本记录、载体集合里没有该会」的条目（[Q30](../06-待决事项.md) 的存量缺口）；它解释的是过滤，不是上游数据缺失。

- **触发重估的信号**：① 库超过 5 万条记录、单次本地检索超过 1 秒；② `--venue` 成为高频入口，且 `venue_filtered_out` 长期大于 `matched`；③ 出现「预算 5000 仍不够」的真实查询（那时先提高默认值，再评估 `work_summary`）。
