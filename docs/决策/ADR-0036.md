# ADR-0036　正文检索走 `works/` 文件扫描；SQLite 的 FTS5 只管标题、摘要与翻译

**状态**：accepted（2026-10-15）

> **范围更正**：本条中"FTS5 索引标题、摘要与翻译"的表述以 [ADR-0042](ADR-0042.md) 为准——只索引英文原文（标题、摘要），翻译不进索引；派生文本的落点见 [ADR-0045](ADR-0045.md)。

- **决策**：正文检索**不进 SQLite**，直接对 `works/` 下的 `paper.md` 做线性扫描（子串或正则）。sidecar 的 FTS5 继续只索引标题、摘要与翻译。
  - 接口：`search --in meta|body|both`，**默认 `meta`**。三个取值是**两个数据源的三档开关**，不是同一档的宽窄：

    | 取值 | 元数据一路（FTS5：标题、摘要） | 正文一路（扫 `works/` 下的 `*.md`） | 结果集 |
    |---|---|---|---|
    | `meta` | 参与 | 不参与 | 元数据命中 |
    | `body` | 不参与 | 参与 | **只**由正文命中决定 |
    | `both` | 参与 | 参与 | 两路并集（按 `work_key` 去重） |

    - **非文本过滤对两路是同一套**：`status='live'`、`--source` 与日期窗（`--since-years` / `--lookback-days`）在元数据一路判「某条成员记录满足」，在正文一路判「该 work 的某条成员记录满足」；venue / 作者 / 引用阈值 / 撤稿在合并之后统一判。
    - **没有检索式时三档同义**：列出本地库——正文一路没有词可扫。
    - **`body` 不联网**：正文只存在于本地语料，所以 `--refresh auto` 在 `body` 档不采集（显式 `true` 仍按字面执行）。
  - 命中返回 `work_key` + **上下文片段**（命中位置 ±60 字符）。
  - 两路结果合并后排序；正文一路用命中次数做粗排序。

- **实测依据**（本机，脚本 `experiments/m1.5/24_body_scan_bench.py`，语料为 M1.5 已文本化的真实产物）：

  | 指标 | 值 |
  |---|---|
  | 语料 | 24 篇 `paper.md`，3.21 MB（单篇 48 KB–400 KB，均值 140 KB） |
  | 全量扫描（关键词 `attention`，48 处命中） | **12.3 ms**（5 次中位数） |
  | 全量扫描（无命中） | **11.6 ms** |
  | 外推 100 篇 ≈ 14 MB | ≈ 49 ms |
  | 外推 500 篇 ≈ 68 MB | ≈ 246 ms |
  | 外推 1000 篇 ≈ 137 MB | ≈ 493 ms |

- **理由**：
  1. **覆盖范围已由 [ADR-0035](ADR-0035.md) 限定**：只有被要过的论文才有全文，语料天然是几十篇量级。10³ 篇全文意味着有人主动要过 1000 篇——短期内不会发生，而到那时扫描也才 0.5 s。
  2. **比建索引还便宜**：11–12 ms 已经低于任何索引方案的固定开销，而索引本身还要建、要维护、要处理失效。
  3. **`works/` 是投影，删掉重建后自动重新可搜**——不存在"重建索引"这一步，也就没有"索引与字节不同步"这个故障模式。
  4. **中文零配置**：子串匹配天然覆盖中文，不需要 FTS5 的 `tokenize='trigram'`，也没有 <3 字查询失效的问题。
  5. **片段随手就有**：命中位置在扫描时已知，切成上下文片段是零成本；而 contentless FTS5 恰恰给不出片段。

- **代价**：
  1. 只能子串 / 正则，**没有 FTS5 的布尔、NEAR、词干与 bm25 排序**。
  2. 每次查询都是全量线性扫描，没有增量；语料变大时开销线性上升。

- **触发重估的信号**（任一出现即重新评估）：
  - 全文语料 > **500 篇** 或 > **100 MB**；
  - 单次扫描耗时 > **1 s**；
  - 出现"必须按布尔/邻近检索正文"的真实需求。

- **备选方案（当前不采用）**：contentless FTS5（`content=''`，只存倒排索引、回指 `bytes/`）。
  - **好处**：查询复杂度与语料规模脱钩。
  - **不采用的理由**：① `snippet()` / `highlight()` 不可用——命中了却拿不到上下文，agent 必须读整个 `paper.md`（均值 140 KB）才知道命中在哪，这一下比扫描本身更贵；② 删除语义别扭（SQLite 3.43 之前 contentless 不支持 `DELETE`）；③ 中文仍需 `trigram` 且 <3 字失效；④ 多一套索引要维护（全文落盘时写、重转时更新、拆组时跟着动）。
  - **复用时可以保留的部分**：倒排索引的粒度应当按 `work_key` 而不是按文件路径——否则拆组会让索引指向失效路径。
