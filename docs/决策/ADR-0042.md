# ADR-0042　v1 只支持英文检索：FTS5 用默认分词器，中文翻译不进索引

**状态**：accepted（2026-10-15）

- **决策**：
  1. **检索一律用英文**：由 agent 侧负责把用户的中文表述翻成英文关键词再检索（写进 SKILL.md 的硬规则）。检索接口不接受「自己处理中文」的责任。
  2. **FTS5 用默认 `unicode61` 分词器**，不做 `trigram`、不接 `jieba`。
  3. **索引只覆盖英文原文**：标题与摘要。**中文翻译与中文摘要照常生成、照常留在 `derived_content.text`，但不进 FTS5 索引**——它们是给人读的，不是检索入口。
  4. **正文检索不受影响**：它走 `works/` 文件扫描（[ADR-0036](ADR-0036.md)），子串匹配天然覆盖中文。

- **理由**：
  1. **中文分词的复杂度买不到东西**：两个候选都有硬伤——`trigram` 是内置但 <3 字查询失效；`jieba` 要引第三方依赖（与[开发/约定](../开发/约定.md)「核心链路仅用标准库」冲突），且新术语（「世界模型」「多智能体」）恰恰是词典最抓不住的东西。
  2. **索引中文只会让索引变大，不会让它更有用**：查询是英文，中文条目永远不会被匹配到。把整篇中文翻译塞进 FTS5 是纯开销。
  3. **跨语言检索的收益可以后补**，而且后补的方式不是分词——是把查询也变成英文去匹配英文原文，这正是决策 1 要求 agent 做的事。

- **代价**：
  1. **中文表述检索不到中文摘要**：用户问「我之前存的那篇讲世界模型的」，agent 必须先把它变成 `world model` 才搜得到。这是 SKILL.md 的责任，不是接口的。
  2. 若日后确实需要中文检索，回退路径是清楚的：给 `derived_content.text` 单建一张 `trigram` 的 FTS5 表，**不动英文那张**。

- **备选方案（当前不采用）**：中文摘要用 `tokenize='trigram'` 单独建表 + `LIKE` 兜底短查询。
  - **好处**：中文表述可以直接检索中文摘要。
  - **不采用的理由**：它解决的是一个当前不存在的需求（检索入口是英文），却要付出索引膨胀与两套分词并存的代价。
