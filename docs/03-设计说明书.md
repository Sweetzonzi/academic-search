# 设计说明书 —— academic-search

> 本文回答"怎么做"。需求与验收见 [01-需求说明](01-需求说明.md)；所依据的事实与实测数据见 [02-现状与调研](02-现状与调研.md)。

## 1. 设计目标与约束

**目标**：实现[项目定位](01-需求说明.md#0-项目定位)——面向本课题组的 LLM 文献检索与阅读辅助技能；满足 R1–R11 与 N1–N4，且满足[验收标准](01-需求说明.md#5-验收标准)。

**关键约束（来自 [02](02-现状与调研.md)）**：

| 约束 | 影响 |
|---|---|
| Zotero 9.0.4 本地 API 只读，库未同步无 API key | 写入通道当前不可用；升级 10.x 是前置条件 |
| Zotero schema 为固定字段集 EAV | 派生数据必须另存（→ D1） |
| OpenAlex 按次计费、无 key 每日 $0.10 | 必须申请 key；filter 优先、批量刷新、结果缓存 |
| arXiv 每 3 秒 1 请求、新文章午夜后可见 | 一天一次足够；必须缓存 |
| SQLite FTS5 中文需 trigram，且 2 字词失效 | 中文检索方案须带 LIKE 兜底或预分词 |
| 运行时缺 `requests`/`PyYAML`/`pyzotero`，无 uv | 核心链路只用标准库 |
| 本地库仅 5 条目 | 定位为"锚"，而非管理主体 |

## 3. 设计决策（ADR）

每条格式：**决策 / 理由 / 被否决的备选 / 代价**。

### D1 采用「Zotero + sidecar + blob 目录」三层存储，而不是单一存储

- **理由**：Zotero 的 `itemData` 是固定字段集 EAV，**结构上装不下**"中文摘要 + 模型版本 + 源哈希"这类任意派生字段；候选池、评分、引用边属于"工作台状态"，不该成为用户资产。
- **否决**：① 全部塞进 Zotero（`Extra`/笔记）→ 污染库、无类型化列、无法 SQL 查、随导出泄漏（[02 §2.3](02-现状与调研.md) 证实 Extra 会被解析）；② 自建完整条目库 → 违背 R8。
- **代价**：多一个文件与一层 join；需要"权威边界"纪律（§4.3.2）。

### D2 采用「确定性 CLI + 薄 SKILL.md」，而不是常驻 MCP

- **理由**：分页、限流、去重、幂等、事务、预算应由代码保证，LLM 只做查询扩展、筛选与总结；上下文成本上 MCP 约 13,448 tokens/请求，而 skill 目录仅 frontmatter 约 98 tokens、正文按需 1,368（[02 §5](02-现状与调研.md)）。
- **否决**：MCP server（低频高价值场景常驻代价过高）；"把逻辑写进 SKILL.md 让 LLM 自行编排"（不可复现、不可测试、易烧额度）。
- **代价**：需维护 CLI 参数、JSON 契约与退出码约定。

### D3 作品身份：`record_uid` 确定性派生；`work` 直接以**首领记录的 `record_uid`** 为键；第三方 ID 只作别名

- **决策**：分三层，且**没有任何随机铸造的 id**——
  - **记录层 `record`**：任何来源命中都写一行，键 `(source, source_id)`，原始元数据原样保留，**只增不改**；其对外 id `record_uid = base32(sha256(source ‖ source_id))`（定长、路径安全、**可复现**）。
  - **分组层 `work`**：一组记录 = 一篇作品。**`work_key` 直接取组内"最早见到"的那条记录的 `record_uid`**，不另铸 id；分组是**可随时重新分组的视图**。
  - **标识层 `record_ident`**：OpenAlex `W…` / DOI / arXiv ID / PMID / S2 CorpusId 全部是**别名**，`(ns, value)` 唯一，回答"这条网络结果记过没有"——一次索引命中。
- **理由**：
  1. **record 的身份就是它的来源坐标** `(source, source_id)`，这个事实永不改变 → 派生值永不改变，因此**可以**确定性派生。派生在这里只是**格式归一化**（单列、定长、路径安全），不是去重手段。
  2. **work 的身份是一个会被修改的分组决定**，无法从任何稳定量派生；但它**也不需要铸造**——用首领记录的 `record_uid` 即可，因为"最早见到的那条"在常态路径（新记录加入）下不会变。
  3. **收益：整个身份层可复现。** 两台机器看同一批来源 → 同样的 `record_uid`、同样的 `work_key`、同样的 `blobs/` 路径 → 导出文件天然对得上；**删库重建后 id 与路径完全一致**。随机 id 做不到这一点，而它换来的只是"work 与 record 概念上彻底解耦"，当前需求用不到。
  4. 第三方 ID 仍不能当主键：实测被合并/删除的 OpenAlex Work ID **返回 404 且无 `Location` 头**（官方删除日志 5,231 万条中取 5 个真实 ID 复测全部 404，存活对照 200），且 2025 年 Walden 切换后**不再提供"旧 ID → 新 ID"映射**（[05 §8.1](05-实验记录-文本化.md)、[02 §3.5](02-现状与调研.md) 第 10–16 条）。
  5. 标题仍不能当身份：跨来源归一化后 **16% 的记录与别的 DOI 共用同一个标题 key，最大一组 7 篇不同论文**；反方向 **约 1/3 的论文标题在预印本 → 正式版之间会变，其中 11% 无法用归一化救回**（[05 §8.3](05-实验记录-文本化.md)）。
- **首领规则（三条，必须实现）**：
  1. 组的首领 = **组内最早见到的那条记录**；`work_key` 永不被改写。
  2. **禁止硬删记录**——删除一律标 `record.status='tombstone'`。否则首领消失会让 `work_key` 失效。
  3. **合并 = 重定向，不是改名**：保留较早的（或已挂 Zotero 的）那个组，另一个写 `work.merged_into` 指向它，并把 `work_member` 改指过去。**拆组**是唯一需要"新键"的操作：拆出部分取它自己最早成员的 `record_uid`；只有当那个成员恰是原首领时才需要例外处理。
- **否决**：OpenAlex `work_id` 作主键（404 无跳转）；标题哈希作 uid（两个方向都会错 + 语义不匹配）；派生式 **work** 键（成员一变键就变）；**随机铸造 `work_uid`**（不可复现，换来的解耦当前用不到）；`canonical_key` 列（有了确定性 `record_uid` 与 `record_ident` 之后它是冗余的——需要展示用的 handle 时**按需从 `record_ident` 派生**，不必存）。
- **代价**：① 所有面向用户的查询要经过分组层 join——**写入变简单，读取变复杂**；② 需要一条"重新分组"维护任务；③ `work_key` 与"首领记录是否存在"耦合，靠首领规则第 2 条兜住；④ `blobs/<work_key>/` 是哈希样目录名，要可读就用投影名（§4.10）。

### D4 中文摘要写回 Zotero 时用 **child note**，不改 Abstract 字段、不塞 Extra

- **理由**：child note 不破坏元数据、可批量识别与回滚、点开即读；`Abstract` 字段会覆盖原文摘要且污染导出；Extra 会被行语法解析并随导出泄漏（[02 §2.3](02-现状与调研.md)）。
- **否决**：写入 Abstract；写入 Extra；写成 `.md` 附件（通常不被全文索引，且占附件位）。
- **代价**：条目树笔记变多；若日后开启 Zotero 同步，这些笔记会上传到 zotero.org。

### D5 调度器中立：只约束命令的性质，不规定用哪个调度器

- **决策**：采集入口是一个**无头、幂等、可观测**的 CLI 命令；调度由使用者的现有工具承担——**DSH schedule、Codex 等外部 agent 工具的定时任务、系统计划任务任选，可组合**。
- **理由**：调度是部署选择而非设计约束。只要命令无头、可重入、产物是结构化报告，任何调度器都能驱动它、任何 agent 都能读它。
- **约束三条**：① 无头（不依赖 GUI/TTY/交互）；② 幂等（同参数重跑不产生重复候选与重复入库）；③ 可观测（每次运行产出 `run.json` + markdown 报告）。
- **否决**：把采集逻辑做进某个特定 agent 的会话内（换 agent 就得重写）；要求人在触发点确认（破坏无人值守）。
- **代价**：需维护 run 账本与报告格式稳定性（`SCHEMA_VERSION` 只增不删）。

### D6 默认**不下载 PDF**，按需获取，且只取 OA 版本

- **理由**：元数据 + 摘要足以支撑检索、去重与初筛；避免版权风险、存储膨胀与"两份 PDF 不知哪份是新的"。
- **否决**：全量预下载（成本与合规风险）；完全不下载（精读需要正文）。
- **代价**：精读时一次网络往返；OA 覆盖不足时可能取不到全文（记录原因即可）。
- **落地形态**：promote 出来的是**仅元信息条目**（§4.3.8）；PDF 在首次精读时挂到**同一个条目**上。

### D7 检索入口唯一：`search` / `lookup --scope auto`，内部固定三段顺序

- **理由**：分叉的真正风险是"两个入口"或"同一事实能改两处"；唯一入口 + 按字段划分权威可消除该风险，同时保留"联网前先查本地"的初衷（R9），且本地查询零网络、零费用、毫秒级。
- **否决**：让 agent 分别查询 Zotero 与 sidecar 再自行合并；把本地库镜像进 sidecar 当权威（变成影子库）。
- **代价**：CLI 需实现多后端聚合与结果标注（§4.3.4）。

### D8 权威归属：Zotero 管「我的库」，sidecar 管「领域语料 + 派生数据」

- **决策**：两个语料库、两种权威，而不是某一方通吃；**作品身份由 sidecar 自己持有**（`record_uid` 确定性派生、`work_key` = 首领记录的 `record_uid`，第三方 ID 只作 `record_ident` 别名，见 D3）。`promote` 是**单向复制 + provenance**，不是双向同步。
- **理由**：① Zotero 的价值（人工策展、同步/导出/引用格式化、阅读器与标注）只对人工策展的小库成立；② 机器规模语料塞进 Zotero 会污染库、拖慢 UI，又提供不了图查询；③ 把"我的库"搬进 sidecar 等于放弃 Zotero 的阅读器/标注/Word 插件，并要重建条目模型与导出——正是 R8 要避免的；④ 两库各自权威、单向流动，就不存在"同一份数据两处可改"。
- **否决**：**sidecar 作为唯一权威、Zotero 只当镜像/导出端**——写入 Zotero 的通道约束（10+、HTTP、无跨库事务）一条都不会减少，换权威不解决写入问题，只额外背上镜像维护、附件管理、引用格式化与同步；**双向同步**——冲突不可判定，必然静默丢数据。
- **代价**：需维护 `dateModified`/`version` 快照与 stale 检测；命令上要显式区分 `--scope local` 与 `--scope corpus`。
- **翻转条件（诚实记录）**：如果用户**实际上从不打开 Zotero**、只把它当存档/导出端，则 Zotero 权威的好处不成立而写入约束仍在，此时"以 sidecar 为主、Zotero 仅作导出"更优。见 `决策 8`。

### D9 「我的库」抽象为 `LibraryBackend`，Zotero 是默认实现而非唯一实现

- **决策**：定义 `LibraryBackend` 接口，提供三种实现——`ZoteroBackend`（sqlite 只读副本 + Zotero 官方 API 写）、`FileBackend`（本地 `library/*.md`，YAML front-matter + BibTeX 导出）、`None`（只用语料库）。「我的库」是逻辑概念，**权威随后端而定**。
- **理由**：课题组成员研究方向不同，只需"同一套工具"，不要求同一套文献管理器；把库抽象成接口后工具才能真正分发，而不必强制每人安装并配置 Zotero。
- **否决**：强制所有人用 Zotero（分发门槛高）；只做 Zotero 后端（等于把工具绑定到单一产品）。
- **代价**：多一层抽象与两套后端测试；去重第一层按后端分别实现（读 sqlite 副本 / 读 YAML），但共用同一套 `identifiers.py` 归一化函数。

### D10 全文文本化：原生文本优先 + 随附便携 pandoc + 图随文保存

- **决策**：为 LLM 阅读生成 Markdown，优先走**原生文本源**（arXiv LaTeX 源码 → arXiv/出版社 HTML），PDF→MD 仅作回退；转换器**随工具附带便携 pandoc**；**图件随文落盘并在 Markdown 中相对引用**；转换时**注入锚点**（详见 §4.10）。
- **理由**：本领域论文公式密集，PDF→MD 的公式与双栏排版最易损坏，而 arXiv 实测同时提供 HTML 与 LaTeX 源码；图从原生源取得是矢量/高分辨率原件，优于从 PDF 抠图；锚点是 R7 溯源的前置条件。
- **否决**：只用 PDF→MD（公式失真）；只存文本不存图（看图要重新下载）；把 Markdown 直接塞进 Zotero（不可索引、不可标注、吃同步配额）。
- **代价**：随工具多约 30–50 MB 的 pandoc（`pypandoc_binary` 实测下载 40.9 MB / 解压后 pandoc.exe 221 MB）；需维护正文容器选择器与锚点映射；**pandoc 的原始输出必须经过归一化层**（[05](05-实验记录-文本化.md)）。

### D11 同一文献的多个来源：全部存为记录，派生数据按内容哈希共享，不做破坏性合并

- **决策**：同一篇论文被多个来源命中时，**既不挑一条"最佳记录"、也不把 B 合并进 A**——每条来源记录各占一行（`record`），由分组层把它们归为一个 `work`；**派生数据（翻译、摘要、文本化产物）以源文本的 `content_hash` 为键**，**不指向"最早的那条记录"**；**文件字节按 `sha256` 内容寻址**，相同字节只存一份。
- **理由**：
  1. 写入时**无需任何跨源仲裁** → 插入天然幂等、可乱序、可并行。这是"多个定时任务从不同来源各自入库"能成立的前提。
  2. **没有不可逆操作**：分组错了改分组即可，没有任何数据被销毁。这正好解掉我们批评 OpenAlex 的那个毛病（合并后 404 且无跳转）——我们允许**重新分组**。
  3. **"没变更的部分指向最早那条"是错的**：预印本与正式版内容会变是常态，指向最早记录必然给出**与原文不符的译文**。改为按内容哈希后，原文没变则自动命中、变了则自动重算，而且**顺序无关**（不需要回答"谁最早"）。
  4. 反向来看，破坏性合并的代价不对称：**漏合**（同一篇两条记录）只是浪费、可修；**误合**（两篇共用一个 work）会让它们的 `paper.md`、图件、翻译、笔记、引用边**互相静默覆盖**，且事后不可检测。
- **否决**：只保留一条"最佳记录"（丢溯源、必须破坏性合并）；派生数据按记录 id 缓存（同一段原文在多条记录下重复计费）；"没变更的部分指向最早记录"（原文变更时静默给出错误派生结果）。
- **代价**：① 记录层要防膨胀——**按"来源"去重，不按抓取次数**（同一 arXiv ID 的 v1/v2 是同一条记录，重跑定时任务只更新不新建）；② 面向用户的检索、候选池、阅读列表、Zotero 入库、引用图谱**全部**要经分组层去重，否则同一篇论文会出现 2–4 次。

## 4. 系统设计

### 4.1 数据源层

**检索策略（省额度的硬规则）**：
1. 能用 `filter` 就不用 `search=`（单价差 10 倍）；`search=` 只用于真正的发现式查询，且结果落盘；
2. 一律 `per_page=100` + `select=` 限定字段（仅顶层）；
3. 存在性判定只走结构化 `filter`（DOI/ID/`title.search`），自由文本噪声极大；
4. 深分页用 `cursor=*`，但要设页数上限，不拉全库；
5. 每轮读 `x-ratelimit-remaining-usd`，低于阈值降级为"只跑增量、停探索式 search"；
6. 引用数刷新走批量：`filter=ids.openalex:W1|W2|…`（OR ≤100）。

**发现式查询的构造**：领域画像（关键词/venue 白名单/作者/机构）→ 展开为若干结构化查询；年份窗口按增量策略（见 §4.7）。

**质量闸门**：`is_retracted`、`type`（排除 paratext / editorial / erratum）、`primary_location.source.type`、OA 状态与许可、`fwci` 与 `citation_normalized_percentile`、`counts_by_year` 异常检测（单年暴涨 → 灌水嫌疑）、venue 白名单（领域顶刊顶会 + DOAJ）、venue 黑名单（掠夺性/已知灌水刊）、语言、年份窗口、机构与通讯作者匹配。**输出为分级（A/B/C）+ 理由**，不做二元淘汰；理由随候选落库。

**摘要处理**：OpenAlex 倒排索引按位置还原为文本；arXiv 直接取 `summary`；缺失是正常分支（回退 Crossref/arXiv 或标记"无摘要"）；两者原样缓存。

**一致性校验**：按 DOI 命中后，用标题相似度 + 年份 + 首作者交叉校验；严重冲突 → 标 `metadata_conflict` 进入待确认，不静默采用。

### 4.2 身份与去重层

#### 4.2.1 五层结构（依据 D3 / D11）

| 层 | 键 | 回答什么问题 | 可变性 |
|---|---|---|---|
| **记录 `record`** | `(source, source_id)`；对外 id = `record_uid` | "这条来源记录抓过没有" | 只增不改（重新抓取只更新） |
| **记录标识 `record_ident`** | `(ns, value)` | "这个 DOI / arXiv ID / W ID 命中过哪条记录" | 可增删 |
| **分组 `work` + `work_member`** | `work_key`（= 首领记录的 `record_uid`） | "这几条记录是不是同一篇" | **可随时重新分组** |
| **派生 `derived_content`** | `content_hash` | "这段原文我算过了没有" | 可丢弃重算 |
| **字节 `blob`** | `sha256(字节)` | "这些字节存过没有" | 可丢弃重抓 |

**没有任何随机铸造的 id**（D3）：

```
record_uid = base32(sha256(source ‖ 0x1f ‖ 归一化后的 source_id))[:20]   # 定长、路径安全、可复现
work_key   = 组内最早见到的那条记录的 record_uid                          # 不另铸 id
```

`record_uid` 里哈希只做**格式归一化**（把两个字段压成单列定长），不做去重——`(source, source_id)` 本身已经是唯一键。需要给人看的 handle（比如导出的文件名、对话里的指称）时，**按需从 `record_ident` 派生**（优先 openalex > doi > arxiv），不落库。

#### 4.2.2 写入路径（不需要跨源仲裁）

```
ingest(一条网络结果):
  1) upsert record (source, source_id)          # 幂等；同一来源重跑只更新
     record_uid = base32(sha256(source ‖ source_id))[:20]   # 确定性，不铸随机 id
  2) 写入该记录的全部标识 record_ident          # DOI / arXiv / W / PMID / CorpusId
  3) group(record):                              # 见 4.2.3
       · 命中已有 work → work_member 挂进去（work_key 不变）
       · 未命中 → 该记录自己当首领：work_key = record_uid，写 work + work_member
  4) 记录不再单独出现在任何面向用户的界面里
```
**注意第 3 步的方向**：新记录加入已有组**永远不会**改变 `work_key`（首领 = 最早见到的那条）；只有"一篇全新的论文"才会让新记录成为首领。这就是"不需要铸造 id"的原因。

**去重判据优先级**（`group()` 内部，逐级降级）：

| 级别 | 依据 | 动作 |
|---|---|---|
| L0 | 记录标识与已有 `record_ident` **共享强标识**（DOI / arXiv ID / OpenAlex W / PMID） | 直接归入同一 work |
| L1 | 一方记录的 `locations[]` / `externalIds` **显式指向**另一方（arXiv↔正式版桥） | 归入同一 work，并**把桥对面的标识补进 `record_ident`** |
| L2 | 弱判据：`title_key` 命中 **且** 一作姓氏相同 **且** 年份落在窗口内 **且** 强标识不冲突 | 归入同一 work，`group_reason` 记为弱判据 |
| L3 | 人工确认 | 归组或**拆组**（拆组是一等操作，不是修数据） |

`work_member.role` 里 `primary` = 首领（`work_key` 的来源），`preprint` / `published` / `duplicate` 标其余记录的角色。**首领是按"最早见到"定的，与"哪条是正式版"无关**——展示时用正式版记录的元数据，但 `work_key` 仍来自最早那条。

**年份窗口必须不对称**：实测预印本 → 正式版可以差 3 年（arXiv 2009 → 期刊 2012），也可能出现 **-1**（arXiv 2024-01 → 会议 2023-11），所以用 `[-1, +10]` 而不是 ±1。

**桥的三条实测通道**（从**只有正式版 DOI** 出发反查预印本）：
1. **OpenAlex 单实体 GET** `/works/doi:<doi>` → 同一 Work 的 `locations[]` 里通常同时有 `publishedVersion`（期刊）与 `submittedVersion`（arXiv，`landing_page_url` 含 arXiv ID）。**单实体 GET 免费**，所以分组任务可以跑得很勤，不烧额度。
2. **Semantic Scholar** `/graph/v1/paper/DOI:<doi>` → `externalIds` 含 `ArXiv` / `MAG` / `CorpusId`（免费，共享池易 429）。
3. **arXiv 的 DataCite DOI** `10.48550/arXiv.<id>`（可**直接构造**，不需查询）→ 反查 OpenAlex。注意：Crossref **不认识**这个 DOI（实测 404），且有已知错配案例 → 命中后必须用标题/年份校验。

#### 4.2.3 弱判据的字段与阈值（实测标定）

| 判据 | 单独使用的假阳性 | 说明 |
|---|---|---|
| `title_key`（小写 + 去标点 + 去首冠词） | **16%**，最大一组 **7 篇不同论文** | 只能当**召回键**，不能当判据 |
| `title_key` + 年份 | 4% | **年份是判别力最强的单字段** |
| `title_key` + 一作姓氏 | 12% | 单独加几乎无用，但组合时需要 |
| `title_key` + 一作姓氏 + 年份 | 4% | 建议判据（另加"强标识不冲突"否决） |

⚠️ 两个必须处理的脏数据：① Crossref 标题里会嵌 **MathML / JATS 标记**（实测 `<mml:math>`、`<sup>®</sup>`）→ 归一化前先剥标记，只剥 LaTeX 不够；② 书章节/前言/索引的记录标题本身重复（实测 `Index` 撞 **3 本不同的书**）→ 按 `type` 过滤 + 黑名单。

#### 4.2.4 派生数据的共享规则（替代"指向最早记录"）

```
derived_content(content_hash PK, kind, lang, model_id, prompt_version, glossary_version, text)
content_hash = sha256(规范化后的源文本)          # 摘要原文 / 正文原文，二选一按 kind
```
- 原文**没变** → 哈希相同 → 自动命中，零成本复用；
- 原文**变了**（预印本 → 正式版是常态）→ 哈希不同 → 自动重算；
- **顺序无关**：谁先算出来都一样，不需要知道"谁是最早的记录"。

`content_hash` 与记录/作品解耦，所以同一段原文出现在多条记录、甚至多个 work 下也只算一次。

#### 4.2.5 重新分组（维护任务，可撤销）

触发条件：① 某条记录后来才拿到 arXiv ID / DOI；② OpenAlex 侧发生合并或拆分；③ 人工拆组。

**合并两个组**（键永不改写，只做重定向）：

```
merge(A, B):                              # 保留哪个组当首领？
  keep = A 若 A 挂了 Zotero；否则较早 first_seen_at 的那个
  drop = 另一个
  UPDATE work_member SET work_key = keep WHERE work_key = drop
  UPDATE work      SET merged_into = keep WHERE work_key = drop   # ← 我们自己保留合并映射
  # drop 那一行不删：任何仍引用旧键的旧导出文件都能一跳解析回来
  # 不删任何 record，不覆盖任何原文
```

**拆组**（唯一可能产生"新键"的操作）：拆出的记录集合里取**最早见到**的那条当首领；若那条恰好是原首领（即首领留在原组），则拆出部分临时回到"新论文"分支——此时它的 `record_uid` 本来就是一个可用且唯一的键，直接用即可，**仍然不需要铸造随机 id**。

**禁止硬删记录**：删除一律标 `record.status='tombstone'`（`record` 与 `work` 的行都保留）。这是 `work_key` 稳定性的唯一前提，必须写进实现约束。

#### 4.2.6 复用

`zotero-mcp/src/zotero_mcp/identifiers.py`（MIT，纯标准库，作者声明可外部 import）提供 `normalize_doi` / `doi_match_key` / `arxiv_identity` / `normalize_title_for_matching`。

**缺口**：其标题匹配只做精确折叠，**无编辑距离、无"作者 + 年份 + 副标题"模糊启发式**；其查重走 Zotero 客户端库（Zotero 未运行不可用）→ 离线模糊匹配层须自研（即本节 L2）。

### 4.3 存储层

#### 4.3.1 三分工

| 存储 | 装什么 | 类比 |
|---|---|---|
| Zotero（`D:\ZoteroLib`） | 条目、collection、tag、附件 PDF、笔记、标注、全文索引 | 书架与正式资产 |
| sidecar（一个 `.db`） | 记录、标识、分组、派生文本缓存、引用边、候选池、运行账本 | 卡片柜与借阅台账 |
| blob 目录（`store/<sha256>` + `blobs/<work_key>/`） | 文本化产物与图件：`paper.md`、可选 `paper.html`、`source.tar.gz`、`figures/` | 派生文本的家；与人读的 Zotero 附件分离 |

**blob 的两级布局**（依据 D11）：
- `store/<sha 前2位>/<sha256>` —— **唯一字节存储**，内容寻址，相同字节只存一份（预印本与正式版原文相同、或两个 work 引用了同一份源码时不会重复占空间）；
- `blobs/<work_key>/` —— **给人看的投影**（`paper.md`、`figures/`），实际文件是 `store/` 里的副本或硬链接，**删掉可完整重建**。

产物来自哪条记录写进 `artifact(record_uid, …)` ——所以"这份 Markdown 是 arXiv 源码转的还是出版社 HTML 转的"永远可追溯。

#### 4.3.2 权威边界（依据 D8）

| 语料库 | 规模量级 | 权威 | 内容与访问方式 |
|---|---|---|---|
| **我的库**（人工策展） | 10²–10³ | **Zotero** | 条目、标签、collection、附件、笔记、标注、全文索引；**读** = 只读 sqlite 副本（`items`/`itemData`/`itemTags`/`fulltextItems`）+ `.zotero-ft-cache`；**写** = 官方 API（10+ 本地 / Web API） |
| **领域语料 + 候选池 + 图谱语料** | 10³–10⁵ | **sidecar** | 检索结果、评分与理由、引用边、翻译与摘要缓存、运行账本；SQL + FTS5 |
| 作品身份 | — | **sidecar 自己持有**：`record_uid`（确定性派生）+ `work_key`（= 首领记录的 `record_uid`）+ `record_ident` 别名 | 第三方 ID 会 404（D3），所以身份必须自己拿；第三方 ID 只作可替换的锚点 |

**流动单向**：`领域语料 --promote--> 我的库`（带 provenance、可回滚）；反向只有"读"。**promote 以 work 为单位**（一个 work 只对应一个 Zotero 条目），而不是以 record 为单位。

**冲突规则（元数据，四条）**：① **人工优先**——Zotero 侧编辑永远胜出；② **不合并、只失效**——发现条目变化（`dateModified`/`clientDateModified`，10+ 另有本地 `version`）即把相关缓存标 stale 重算；③ **写入显式**——改 Zotero 元数据必须显式命令，默认**只补空、不改非空**；④ **冲突暴露**——与 Zotero 不一致的外部元数据标 `metadata_conflict` 并进报告。

**没有任何字段同时存在两处**；唯一冗余是 `work_key ↔ itemKey` 指针。**「我的库」的权威由后端决定**（D9）：Zotero 后端下是 Zotero；FileBackend 下是 `library/` 目录中的 Markdown + YAML。

**发现正式版时的行为**（承接 D11，典型场景）：新记录进记录层 → 分组任务用 L0/L1 判据归入已有 work → 派生数据按 `content_hash` 决定复用还是重算 → **Zotero 条目不动**，只写一条待确认提示（"已发现正式版 DOI …，是否更新条目？"），由人决定是否补 DOI/venue/卷期。**预印本的原文与日期永不覆盖。**

#### 4.3.3 sidecar 三条原则

1. **「我的库」侧没有只此一份的数据**：sidecar 里全是可重建的派生数据，整个文件删掉，用户库毫发无损。而且因为 id 是**确定性**的，重建之后连 `record_uid` 与 `work_key` 都和原来一样（唯一例外是"拆组"这种人工决定，见附录 A 重建流程）；
2. **不重复 Zotero 已有的东西**：元数据以 Zotero 为准，PDF 只存 Zotero 一份；
3. **只装可重建的派生数据**。

工程要求：外键用 `libraryID + itemKey`（不用自增 `itemID`）；**按 `Zotero-Server-ID` 分区**（10+ 版本号为本机局部版本）；`schema_version` + 迁移脚本；单写者 + WAL。

#### 4.3.4 单一检索入口（消除"分叉"）

```
lookup(DOI | arXiv ID | 标题 | 关键词 | 标签)
  ① 本地 Zotero（只读副本，离线、零成本、毫秒级）
       命中 → 返回条目 +「已在库」+ 附 sidecar 中文摘要（若有）
  ② sidecar 候选池（避免重复推荐、避免重复计费）
       命中 → 返回候选 + 评分与理由
  ③ 均未命中 → 联网 OpenAlex/arXiv，结果先与 ①② 去重，再落候选池
```
落点映射：**DOI/arXiv ID** → Zotero 的 DOI 字段 + sidecar 的 `record_ident`，两路合并去重；**标签** → 只查 Zotero（标签权威在该处，agent 自动打的标签也写进 Zotero）；**关键词** → Zotero 标题/作者 + `.zotero-ft-cache`，加 sidecar 中文摘要 FTS5。

**真正需警惕的三件事（属去重问题，非存储分叉）**：① 用户自己导入的重复条目（Zotero 自带检测只做 DOI/标题精确折叠，超 5000 条拒绝扫描）；② 预印本与正式版各存一条；③ Zotero 条目与 OpenAlex 记录是同一篇。

**这三件事现在统一由分组层处理**（§4.2）：前两件靠 L0/L1 判据归组，第三件靠 `record_ident` 里 `(ns='openalex')` 命中。**面向用户的三个入口——检索结果、候选池推荐、阅读列表——都返回 `work` 而不是 `record`**，所以同一篇论文不会因为来自两个源就出现两次；而"它来自哪几条记录"随时可查（这既是溯源，也让判据可以被人工复核）。

#### 4.3.5 中文摘要的可见性

**默认看不到**（sidecar 不出现在 Zotero UI）；写回需 Zotero 10+ 写入通道。四种位置：

| 位置 | 可见性 | 代价 | 结论 |
|---|---|---|---|
| **child note** | 条目面板 Notes 区，点开即读，可被搜索命中（建议 `Everything` 模式） | 条目树变长 | ✅ 默认（标题固定前缀，如「AI 中文摘要」） |
| Abstract 字段 | 最显眼（面板顶部，列表可加列） | 覆盖原文摘要、污染导出 | ❌ |
| Extra 字段 | 列表可加列扫读 | 行语法解析 + 导出泄漏 | ⚠️ 仅极短单行 |
| `.md`/`.html` 附件 | 附件区双击打开 | 通常不被全文索引、占附件位 | 备选（长报告） |

**中文检索的实测约束**：FTS5 默认分词器对中文 0 命中 → 用 `tokenize='trigram'`；但 <3 字查询仍失效 → `LIKE '%…%'` 兜底，或先用 jieba 分词再索引。

#### 4.3.6 候选池状态机

**候选池是"检索结果 → Zotero"之间的暂存区**，用一张 `candidate` 表记录状态。状态集合刻意做小：

| 状态 | 含义 | 谁设置 | 后续行为 |
|---|---|---|---|
| `new` | 新入池，待处理 | 采集 run 自动 | 出现在推荐列表 |
| `promoted` | 已写入 Zotero | `promote` 命令 | 之后命中走**第一层**（本地库），不再走候选池 |
| `parked` | 本次决定不入库，但保留可查 | LLM 初筛 / 用户 / 自动规则（如质量分级 C） | 默认不再主动推荐；仍可被显式搜索到 |
| `hidden` | 明确不再推荐（抑制） | 用户 | 进入抑制名单，默认长期有效（可选 6–12 个月后允许重新浮现） |

**是否引入 `parked`/`hidden` 取决于 `决策 6`（入库策略）**：
- 若选**全自动入库** → 状态集合退化为 `new → promoted`（+ 失败重试），没有人工环节；
- 若选**候选池 + 筛选**（推荐）→ 需要 `parked`/`hidden` 来表达"看过但不要"，否则每轮都会重复推荐同一批论文；
- 若选**只入语料库、不入 Zotero** → `new → parked` 为主，`promoted` 变成可选动作。

保留状态而不是删除记录的原因：① 避免重复推荐与重复计费；② 可复盘"当时为什么不要"；③ 研究兴趣会变，`hidden` 可设过期。

#### 4.3.7 候选池 → 入库（promote）

```
search → candidates(sidecar：评分/分级/理由/来源)
  → [LLM 初筛 或 用户确认，取决于决策 6]
  → promote：写入专用 collection（如 `Agent Inbox/<领域>`）+ provenance tag（如 agent/2026-10）
             + 记录 run_id / 决策理由 / 原始响应快照
  → 回滚：按 run_id 找 itemKey → 删除（Zotero 删除进回收站，安全）
```
**这是最重要的安全阀**：agent 往用户的学术资产库里写东西，必须"可批量识别、可批量撤销"；绝不写进用户现有 collection。

#### 4.3.8 仅元信息条目与按需附件

- Zotero 里"元数据条目"与"附件"是独立 item，**没有任何字段要求条目必须有附件**（[02 §2.2](02-现状与调研.md)）。
- **有元数据即可**：检索、collection 归类、去重、引用与参考文献导出、元数据同步（不占文件配额）、写 child note。**缺附件则不能**：阅读标注、该条目全文检索、页码定位。
- **策略**：默认 promote 为仅元信息条目；PDF 按需获取（[五级回退](02-现状与调研.md)），作为子附件挂到**同一条目**，不重建条目、不影响去重键、不产生第二份 PDF。
- **工程要求**：全文相关查询一律 **LEFT JOIN**；`text_cache` 与 `zotero_link` 允许 `zotero_attachment_key` 为空。

#### 4.3.9 复现语义：第二次检索到同一篇（且未入库）会发生什么

命中第三层 → **不新建候选、不重新计费检索、不重新调 LLM**，只做"刷新 + 决策保持"。

| 动作 | 内容 | 成本 |
|---|---|---|
| **刷新（每次做）** | `cited_by_count`、`counts_by_year`、`fwci`、`citation_normalized_percentile`、**`is_retracted`（必查，安全信号）**、`oa_status` 与 `pdf_url`（PDF 可能新出现）、`type`/venue（预印本可能已发表）、`refreshed_at`、`seen_count`、`last_seen_at` | 可批量按 ID 取，约 `$0.0001`/百条 |
| **重算（因输入变化）** | 质量分级（输入含引用信号）；引用边（若在图谱范围） | 纯规则计算，0 LLM |
| **复用（缓存命中）** | 中文翻译、各粒度摘要、嵌入向量 | 0 成本 |
| **保持（绝不重置）** | `status`（尤其 `parked`/`hidden`）、`staged_at`、决策理由、`run_id` | — |

**重新翻译的唯二触发条件**：① 源文本变了（OpenAlex 补全摘要；**arXiv 出 v2 改了 `summary`**）；② 生成参数变了（`model_id` / `prompt_version` / `glossary_version` / `target_lang`）。

**关键边界（最易犯的错）**：**引用数绝不能进缓存键**。缓存键是 `sha256(源文本 ‖ 目标语言 ‖ 模型 ‖ 提示词版本 ‖ 术语表版本)`；若把整条记录哈希当缓存键，每次引用数变动都会触发全量重翻译。

**与 Zotero 的衔接**：`promote` 后标 `promoted` 并写 `zotero_link`（**work 级**，一个 work 只对应一个条目），此后命中走第一层；若用户在 Zotero 中删除该条目 → 标 `promoted_then_removed`，**不自动重新入库**（尊重删除决定），仍留在候选池可查。

### 4.4 缓存层

**键设计**（照搬 `zotero-mcp/src/zotero_mcp/fulltext_cache.py` 的内容哈希 + profile + 落库即逐出；其原则："文件变了必然换 hash，绝不供给陈旧文本"）：

```
content_hash = sha256(规范化后的源文本)      # 摘要原文 / 正文原文，按 kind 各算一次
derived_key  = (content_hash, kind, lang, model_id, prompt_version, glossary_version)
```
把 `prompt_version` 纳入键，是避免"改了提示词却读到旧摘要"的关键；**把 `content_hash` 而不是 `record_uid` 放在首位**，是 D11 的落地点——同一段原文出现在多条记录（预印本 / 正式版 / 出版社）下只算一次，原文一变自动失效，且**与谁先算出来无关**。

| 缓存 | 失效触发 | 备注 |
|---|---|---|
| 翻译（标题/摘要/关键词） | **源文本内容哈希**、目标语言、模型或 `prompt_version` 变化 | **不整篇翻译**（成本 + 版权） |
| 摘要（分层） | 同上 + 摘要粒度（一句话/贡献点/方法-结果-局限） | 粒度不同即不同条目 |
| 抽取全文 | 附件/源文件内容哈希变化 | 原始文本永久可复用 |
| 向量 | 嵌入模型或维度变化 | 需重建索引 |

**内容哈希怎么算**（决定缓存命中率，必须固定下来）：先剥标记（MathML/JATS/HTML）→ NFKC → 统一连字符 → 折叠空白 → 大小写策略按 `kind` 定（摘要可比大小写不敏感，正文不行）。**哈希的是"规范化后的源文本"，不是原始字节**——否则同一段摘要只因换行不同就会重算。

**全文通道优先级**：① 原生文本源文本化（arXiv LaTeX 源码 / HTML，见 §4.10）→ ② `.zotero-ft-cache`（零成本，本机 6/6 命中）→ ③ Zotero 全文 API（10+ 可 `GET/PUT …/fulltext`）→ ④ PDF 自解析（`pymupdf` 已装）。

**成本控制**：批量走 Batch API；每个 run 设 token 预算，超限降级为"只翻标题"。

### 4.5 检索与命令接口

| 命令 | 作用 | 关键约束 |
|---|---|---|
| `search` | 按领域/关键词/作者/机构检索，返回分级候选 | `--since`、`--limit`、`--source`、`--scope auto\|local\|corpus` |
| `lookup` | 按 DOI/arXiv ID/标题取条目或候选 | 走 §4.3.4 三段顺序 |
| `dedupe` | 对给定集合做分组判定（离线优先，只读 sqlite，Zotero 不必运行） | 返回"归入哪个 work / 新建 work"及判据 |
| `stage` | 候选落 sidecar（带理由与原始响应） | 幂等，唯一索引 |
| `promote` | 候选入 Zotero（专用 collection + provenance tag） | `--dry-run` 先行；可按 `run_id` 回滚 |
| `translate` / `summarize` | 生成派生文本并缓存 | 预算上限；`--no-note` 控制是否写回 Zotero |
| `read` | 取条目全文（优先 `paper.md`）或指定页/段落 | 输出必须带 itemKey + 锚点（页码或章节号） |
| `convert` | 取原生文本源并转 Markdown（含图件落盘、锚点注入） | `--source auto\|latex\|html\|pdf`；转换器版本进缓存键 |
| `export` / `bundle` | 导出给他人或其他工具的产物 | `--format md\|zip\|bibtex\|ris\|csljson`；`md/zip` 包内自带 `figures/` |
| `sync` | 增量采集（无头，供任意调度器调用） | 水位 + `run_id` + `run.json` |
| `graph` | 引用边抓取、脉络查询、导出 Mermaid/Graphviz | 节点上限与分页取样 |

**输出契约**：单一信封 `{ok, command, schema: 1, data | error{message, code}}`，成功失败都写 stdout，日志写 stderr，`SCHEMA_VERSION` **只增不删**；退出码 0 成功 / 1 失败（可细分）。

**依赖策略**：核心链路仅用标准库（`urllib.request`、`json`、`sqlite3`、`xml.etree`）；重活（向量、PDF 版面、Zotero 客户端库）放独立虚拟环境按需启用。

### 4.7 触发方式与运行账本

**调度器中立**（D5）：采集命令必须**无头 + 幂等 + 可观测**；DSH schedule、外部 agent 定时任务、系统计划任务任选、可组合。

```
# 采集（可被任意调度器无头调用）
academic-search sync --profile <领域> --budget <n>
  → 抓取增量 → 去重 → 分级 → 入候选池 →（可选）翻译摘要
  → 写 reports/<date>.md + run.json

调度器（任选，可组合）：
  · DSH schedule（如每周一 09:00：读最新 run 报告 → 要点提炼 / 异常提示 / 推荐阅读）
  · 外部 agent 工具自带的定时任务（如 Codex 等），由它调用命令或读取报告
  · 系统计划任务（Windows 任务计划程序 / cron）
```

**幂等与水位**：sidecar 存 `last_success_watermark` 与 `run_id`；每次 run 独立事务；唯一索引保证重跑不产生重复候选。

**增量策略**：`from_created_date`/`from_updated_date` 疑似付费层 → 采用"`publication_date` 回看 N 天 + 本地去重兜底"，并记录已抓取的 OpenAlex ID（`record_ident(ns='openalex')`）以避免重复计费。注意 **`publication_date` 是正式版日期**（实测 arXiv 2009 的论文在 OpenAlex 里是 2012），所以"新论文"的时间窗必须用 arXiv 的日期。

**限流与预算**：单次 run 的请求数/并发/退避上限显式配置；每轮读 `x-ratelimit-remaining-usd` 降级；arXiv 严格 3 秒间隔且一天一次足够；Crossref 走 polite 通道；S2 失败不阻断主链路。

**观测**：JSONL 结构化日志 + markdown 报告 + **结构化 `run.json`**（使"外部 agent 只读消费"成为可能）：新增候选、去重拦截、入库数、失败源与原因、token 与费用消耗。

### 4.8 引用图谱与研究脉络（未来，R10）

**数据基础**（[02 §3.4](02-现状与调研.md)）：后向 `referenced_works`；前向 `filter=cites:<OpenAlex W id>`（注意：这里的 `<…>` 是 **OpenAlex 自己的** work id，从 `record_ident(ns='openalex')` 取，不是我们的 `work_key`）；`related_works`（相似推荐，非引用关系）；Crossref `reference[]` 补充。旧 `cited_by_api_url` 勿用。

**存储**：引用边的节点统一为 `work_key`（分组层），表在附录 A：`citation_edge(src_work_key, dst_work_key, source, retrieved_at)`。抓回来的 OpenAlex ID 先经 `record_ident` 解析成 `work_key`——**没解析出来的目标节点暂存为待解析引用**，等它被检索到时再补，不要为了建图去拉全库。

**已知的坑（实测）**：`referenced_works` 可能短于原文参考文献表；被引数会随对方合并/删除而变动，所以引用边要有 `retrieved_at` 并可刷新。

**四种算法（成本递增）**：① 向后引用链；② 向前被引链；③ **主路径分析（main path analysis）**——学术谱系标准做法，给技术演进主线；④ 共被引 / 文献耦合聚类（识别流派）。

**可视化**：先出 **Mermaid / Graphviz**（零依赖、可入文档、diff 友好）；交互式图留待需要时。**大图必须裁剪**：路径裁剪 + 时间轴分层 + 每节点一句话摘要。

**成本**：引用边抓取属 `list+filter` 档（$0.10/千次），无 LLM 成本；被引 2 万条的节点分页取样而非全量展开。

### 4.9 可信、合规与隐私

**"可信"的可执行定义（N1）**：
- 每条结论可落到 `{work_key / DOI / arXiv ID, itemKey, 页码或段落}`；无出处的断言不输出（写进 SKILL.md 硬规则，CLI 提供 `--require-citation` 强制）；
- 候选项携带来源与获取时间，原始响应留档；
- 质量信号进决策但不越权：闸门给"分级 + 理由"，取舍留给人或显式配置的策略；
- 已知缺陷显式暴露：DOI 与标题不一致、缺 DOI、venue 缺失 → 标 `metadata_conflict`，不静默采用。

**合规**：
- 只取 OA 版本；DOI→PDF 五级回退（OpenAlex `best_oa_location` → Crossref TDM → Unpaywall → arXiv/PMC → 放弃并记录）；
- **arXiv 禁止自行托管/分发 PDF**；**PMC 只允许 E-utilities / OAI-PMH / BioC 等指定服务做自动化批量抓取**；Unpaywall 须真实 email；
- 翻译/摘要属派生使用，默认只对标题与摘要做，不整篇翻译再分发。

**隐私（N3）**：本地库内容默认不出网；送往云端 LLM 的内容可枚举、可关闭；提供"全离线"档（本地嵌入 + 本地翻译模型），代价是质量与速度。

### 4.10 全文文本化与图件流水线

**目标**：让 LLM 能读全文（PDF 对 LLM 不友好），同时让人能在 Zotero/浏览器里读同一篇的文本版；图件随文保存。

**分层来源（先原生文本，后转换）**：

| 层 | 来源 | 做法 | 保真度 |
|---|---|---|---|
| 1 | **arXiv LaTeX 源码** `/e-print/<id>`（实测可用） | 便携 pandoc `-f latex -t gfm --extract-media=figures/` | ★★★ 公式原生、图为矢量原件 |
| 2 | **arXiv HTML** `/html/<id>`（实测可用） | pandoc `-f html -t gfm` | ★★ MathML → LaTeX |
| 3 | OA 出版社 HTML（MDPI / Frontiers / PLOS、中文期刊官网） | 同上 + 正文容器选择器 | ★★ |
| 4 | Zotero `.zotero-ft-cache` | 直接作纯文本（无结构，够检索） | ★ |
| 5 | PDF → MD（PyMuPDF4LLM / marker / MinerU） | 回退 | ★ 公式与双栏易坏 |
| 6 | 扫描件 OCR | 最后手段 | ☆ |

**转换器**：随工具附带**便携 pandoc**（单文件置于 `tools/`，不改系统环境）；`converter` + `converter_version` 进缓存键（复用 `text_cache.extractor*` 字段），换更好的转换器可触发重转。

**必做装配五步**：

1. **抽取正文容器**：arXiv → `<article>`；MDPI → `.html-body`；通用 → `<article>` 或启发式；去掉 nav / footer / cookie 提示 / 推荐阅读；
2. **锚点注入**（R7 溯源的前置条件）：能拿到真实页码时注入 `<!-- page: N -->`；HTML/LaTeX 源注入 `<!-- sec: 3.2 -->` 并**明确标注为近似锚点**；
3. **图件本地化**：`<img>` 与 LaTeX 图片先落到内容寻址的 `store/`，再投影到 `blobs/<work_key>/figures/`，Markdown 用相对路径引用；图注抽成 `captions.json`（可参与翻译与检索）；
4. **元信息头**：YAML front-matter（DOI / arXiv ID / 来源 URL / 抓取时间 / 转换器版本 / 许可备注）；
5. **登记**：写入 sidecar 的 `artifact` 表（见附录 A），**记录这份产物来自哪条 record**。

**产物布局**（Markdown 与图绑定，便于整体打包给同学）：

```
store/<sha 前2位>/<sha256>        # 唯一字节存储（内容寻址，相同字节只存一份）
blobs/<work_key>/                 # 给人看的投影，删掉可重建
├─ paper.md          # 给 LLM 读的派生文本（由最优来源记录转换而来）
├─ paper.html        # 可选：给 Zotero 索引与标注（Zotero 索引 HTML，不索引 .md）
├─ source.tar.gz     # 可选：arXiv LaTeX 源码（仅个人使用）
└─ figures/
   ├─ fig-01.svg     # 矢量原件（来自 LaTeX/HTML 源）
   ├─ fig-03.png
   └─ captions.json  # 图号 → 图注文本
```

**选择哪条记录做"代表"**：同一 work 可能有多条记录各自能给全文（arXiv 源码 / 出版社 HTML / PDF）。默认优先级见 §4.10 的六层来源表，**选中哪条写进 `artifact.record_uid`**；若换了代表来源，产物按新记录的 `content_hash` 重新生成，旧产物留在 `store/` 里不删（可能仍被其它 work 引用）。

**与 Zotero 的关系**：Zotero 附件只放**人要看 / 要搜**的东西——HTML 快照（可索引、可标注）与 PDF 原件；Markdown 与图件留在 blob，避免同步配额与二进制污染（依据见 [02 §2.2](02-现状与调研.md)）。

**许可边界**：arXiv 源码/PDF 与出版社 HTML **仅限个人使用，不得随工具或组内分享再分发全文**；分享时只发元数据 + 自行生成的中文摘要/笔记 + 引用链接（配合 `export --format bibtex|ris|csljson`）。

## 6. 风险登记册

| 风险 | 概率 | 影响 | 缓解 | 触发信号 |
|---|---|---|---|---|
| **Zotero 版本阻塞写入** | 已发生 | 高 | 升级 10.x；否则走候选池 + 人工导入降级路径 | `POST /items` 返回 403/428 |
| **升级 Zotero 触发数据库迁移（不可逆）** | 中 | 高 | 升级前备份 `D:\ZoteroLib`（库仅 2.22 MB）；先在副本上验证 | 升级后 `databaseSchema` 变化 |
| **OpenAlex 额度耗尽** | 高（若无 key） | 中 | 申请 key；filter 优先；批量刷新；读 `remaining-usd` 降级 | 429 或余额接近 0 |
| **元数据错配导致错误入库** | 中 | 中 | DOI↔标题一致性校验；冲突标记待确认；保留原始响应（`record.raw_json`） | 一致性分数低于阈值 |
| **分组误判（同题不同文 / 同文不同题）** | 中 | **低**（D11 后） | 分组是**视图**不是身份：弱判据分组错了就改分组，没有数据被销毁；强标识冲突一律不自动归组 | `dup_suspect` 积压；人工拆组 |
| **首领记录被删导致 `work_key` 失效** | 低 | 高 | **禁止硬删记录**，删除一律标 `record.status='tombstone'`（实现约束 + 契约测试）；`work_key` 永不被改写 | `work` 出现悬空外键；重建后路径不一致 |
| **确定性 id 的取值规则被改动**（改了 `record_uid` 的派生方式） | 低 | 高 | 派生化规则**进 `SCHEMA_VERSION`**，改动即视为迁移：老 id 与老 `blobs/` 路径要能识别并批量重命名；规则本身写进实现约束 | 同一记录在新旧版本下算出不同 `record_uid` |
| **记录层膨胀** | 中 | 中 | 按**来源**去重（`UNIQUE(source, source_id)`），v1/v2 是同一条；重跑只更新 | `record` 行数远超 `work` 行数 |
| **读取路径变复杂（分组层 join）** | 高 | 中 | 三个面向用户的入口统一返回 `work`；分组结果物化，不在查询时现算 | 检索结果出现同篇两次 |
| **学术库被 agent 污染** | 中 | 高 | 只写专用 collection + provenance tag；`--dry-run`；按 run 回滚 | 用户库出现非预期条目 |
| **子笔记污染与同步隐私** | 中 | 中 | 默认仅对 promoted 条目写；`--no-note`；提示同步后果 | 用户开启同步后笔记上云 |
| **采集静默失败** | 中 | 中 | `run` 表 + `run.json`/markdown 报告 + 失败退出码；幂等重跑 | run 缺失或 `status=failed` |
| **Zotero schema 漂移导致读取失效** | 低 | 中 | 启动时校验 `databaseSchema` 与关键表存在性；失败即降级并报错 | 表/列缺失 |
| **sidecar 退化为影子库** | 低 | 中 | "重建一致性"测试；禁止任何权威数据只存 sidecar | 重建后视图不一致 |
| **权威边界模糊 / 双向编辑冲突** | 中 | 高 | D8 四条冲突规则：人工优先、不合并只失效、写入只补空、冲突显式暴露 | Zotero 条目被改后我方元数据不一致 |
| **中文检索失效** | 已定位 | 中 | trigram + LIKE 兜底或预分词 | 2 字查询 0 命中 |
| **全文再分发触发许可问题** | 中 | 中 | 分享只发元数据 + 自产摘要；源码/PDF/HTML 仅留本地（D10） | 导出包中出现全文 |
| **随附 pandoc 的体积与版本漂移** | 低 | 低 | 固定版本随工具分发，并把 `converter_version` 记入产物与缓存键 | 转换输出格式变化 |
| **FileBackend 与 ZoteroBackend 行为不一致**（D9） | 中 | 中 | 同一组契约测试跑两个后端；去重与导出作为共同验收项 | 同一查询在两端命中结果不同 |

## 附录 A：sidecar 完整 schema

```sql
-- 0) 元信息：schema 版本与 Zotero 实例分区
meta(key TEXT PRIMARY KEY, value TEXT);   -- schema_version / zotero_server_id / data_dir

-- ============ 第一层：记录（一条来源记录一行；写入不需要跨源仲裁）============
record(record_uid TEXT PRIMARY KEY,       -- base32(sha256(source ‖ 0x1f ‖ source_id))[:20]
                                          -- 确定性派生：同一来源的同一记录在任何机器上都是这个值
       source TEXT NOT NULL,              -- arxiv | openalex | crossref | s2 | zotero | pdf | ...
       source_id TEXT NOT NULL,           -- 该来源内的 id（arXiv id / W id / DOI / CorpusId / itemKey）
       title, abstract_text, abstract_hash,   -- abstract_hash = sha256(规范化摘要) → 派生共享
       preprint_date, publication_date, venue, type, language, license, is_retracted,
       status,                            -- 'active' | 'tombstone'（禁止硬删，见 D3 首领规则）
       raw_json TEXT,                     -- 原始响应原样保留（可复盘、可重放）
       fetched_at, updated_at,
       UNIQUE(source, source_id));        -- 同一来源重跑只更新，不新建（v1/v2 也是同一条）

-- 记录级标识（一条记录可以有多个：DOI + arXiv + W + PMID）
record_ident(ns TEXT, value TEXT, record_uid TEXT REFERENCES record(record_uid),
             source TEXT, raw_value TEXT, added_at,
             PRIMARY KEY(ns, value));     -- ← 让"这条网络结果记过没有"只需一次索引命中
-- ns ∈ {doi, arxiv, arxiv_doi, openalex, s2, mag, pmid, pmcid, dblp, zotero}
CREATE INDEX idx_ident_record ON record_ident(record_uid);

-- 记录级全文位置（多个来源可能各给一份全文）
record_location(record_uid, url, version, is_oa, license, source_type,
                PRIMARY KEY(record_uid, url));
-- version ∈ {submittedVersion, acceptedVersion, publishedVersion, ''}

-- ============ 第二层：分组（作品 = 一组记录；是视图，可重新分组）============
work(work_key TEXT PRIMARY KEY REFERENCES record(record_uid),
                                          -- ★ 不另铸 id：= 组内最早见到的那条记录的 record_uid
     title_display, abstract_display,     -- 代表值（默认取正式版记录）
     venue_display, type, language,
     preprint_date, publication_date,     -- 两个日期都留（"新论文"用前者）
     cited_by_count, fwci, is_retracted, oa_status,
     group_reason TEXT,                   -- 'ident:doi' | 'bridge:openalex' | 'weak:title+author+year' | 'manual'
     group_confidence REAL,
     merged_into TEXT REFERENCES work(work_key),   -- 合并=重定向，不是改名；我们自己保留映射
     first_seen_at, refreshed_at);

work_member(work_key TEXT REFERENCES work(work_key),
            record_uid TEXT REFERENCES record(record_uid),
            role TEXT,                    -- primary(=首领) | preprint | published | duplicate
            joined_at, join_reason,
            PRIMARY KEY(work_key, record_uid));
CREATE INDEX idx_member_record ON work_member(record_uid);

-- 弱判据召回表：绝不加唯一约束（否则第二篇同名论文会被拒绝铸造或错并入第一篇）
work_title_key(title_key TEXT, work_key TEXT, year INTEGER, first_surname TEXT,
               PRIMARY KEY(title_key, work_key));
CREATE INDEX idx_tk ON work_title_key(title_key);

-- 存疑对（弱判据未达阈值 / 强标识冲突）→ 人工或 LLM 复核后归组或忽略
dup_suspect(work_key_a, work_key_b, score, reason, created_at,
            PRIMARY KEY(work_key_a, work_key_b));

-- ============ 第三层：与本地库的指针（唯一需要与 Zotero 对齐的表，work 级）====
zotero_link(work_key PRIMARY KEY, library_id, item_key, server_id, linked_at, run_id);
CREATE UNIQUE INDEX idx_link_item ON zotero_link(library_id, item_key);

-- ============ 第四层：派生内容（键 = 源文本内容哈希，与 record/work 解耦）====
derived_content(content_hash TEXT,        -- sha256(规范化源文本)；摘要与正文各自一算
                kind TEXT,                -- title_zh | abstract_zh | summary_1line | paper_md | captions_zh
                lang TEXT,
                text,
                model_id, prompt_version, glossary_version,
                record_uid,               -- 第一次算它时是哪条记录（溯源用，不作键）
                created_at,
                PRIMARY KEY(content_hash, kind, lang, model_id, prompt_version, glossary_version));
CREATE INDEX idx_dc_record ON derived_content(record_uid);

-- ============ 第五层：字节与产物（内容寻址）============
blob(sha256 TEXT PRIMARY KEY, bytes INTEGER, media_type, created_at);
-- 实体路径：store/<sha 前2位>/<sha256>

artifact(record_uid TEXT REFERENCES record(record_uid),
         kind TEXT,                       -- paper_md | paper_html | source_archive | figure | captions
         name TEXT,                       -- 'paper.md' / 'figures/fig-01.svg'
         sha256 TEXT REFERENCES blob(sha256),
         source_url, license_note, converter, converter_version, anchor_scheme,
         created_at,
         PRIMARY KEY(record_uid, kind, name));

-- 派生文本的字符数等元数据（正文实体在 store/）
text_cache(content_hash TEXT PRIMARY KEY, record_uid, zotero_attachment_key,
           sha256, char_count, extractor, extractor_version, created_at);

-- ============ 引用边（未来脉络图；节点统一为 work_key）============
citation_edge(src_work_key, dst_work_key, source, retrieved_at,
              PRIMARY KEY(src_work_key, dst_work_key, source));
CREATE INDEX idx_edge_dst ON citation_edge(dst_work_key);

-- ============ 候选池（work 级，避免同一篇被多条记录重复推荐）============
candidate(work_key TEXT PRIMARY KEY, run_id, query, score, grade, reasons_json,
          status, staged_at, decided_at, seen_count, last_seen_at);
-- status ∈ {new, promoted, parked, hidden}   见 §4.3.6

-- ============ 运行账本 ============
run(run_id TEXT PRIMARY KEY, profile, started_at, finished_at, status,
    requests_used, cost_usd, new_candidates, deduped, promoted, regrouped, error);

-- ============ 中文全文检索（trigram 支持中文；<3 字查询用 LIKE 兜底）============
CREATE VIRTUAL TABLE derived_content_fts USING fts5(
    content_hash UNINDEXED, kind UNINDEXED, text, tokenize='trigram');
-- 可选：先用 jieba 分词再写入 unicode61 索引，可支持 2 字词
```

**重建流程**（验证"sidecar 永不权威"）：删除 `.db` 与 `store/`、`blobs/` → 从 Zotero 读条目与附件 → 重新抓取元数据（记录层与标识层重建）→ 重新分组（L0/L1 判据会得到同样的分组）→ 重算翻译/摘要（`derived_content` 若已备份则零成本命中）→ 条目视图应与删除前一致。

**因为 id 是确定性的，重建后 `record_uid`、`work_key` 与 `blobs/` 路径都与删除前完全一致**（D3 的收益）——这是把随机 id 换掉之后才成立的。**唯一例外**是"拆组"产生的新首领：拆组的决定本身不可复现，所以拆组后的 `work_key` 需要一次显式记录（写进 `work.group_reason` 与运行账本），否则重建会得到原始分组。
